# EPIC-013: Роли PM и QA — подготовка решений для человека

## Цель

Четвёртый эпик декомпозиции v1.0 ([ROADMAP.md](../../ROADMAP.md)) и последний **функциональный** — после него остаётся только стабилизация и релиз: автоматизировать роли Project Manager и QA Engineer так, чтобы они **готовили** решения, а человек их **принимал**. Результат: golden path автоматизирован целиком, кроме двух контрольных точек, которые остаются человеческими по [ADR-007](../adr/ADR-007-pm-qa-executors.md) — и это не незавершённость, а замысел.

## Контекст

### Решение, снимающее главный риск: агенты не получают доступа к `apps/api`

[EPIC-012](EPIC-012-human-checkpoints.md) закрылся с зафиксированной предпосылкой: аутентификации нет ([ADR-012](../adr/ADR-012-identity-and-auth.md)), поэтому контрольные точки защищает **только** сетевой allowlist агентской песочницы, и открытие агентам доступа к `apps/api` эту защиту снимет. ADR-007 в разделе «Технический подход» такой доступ предполагала («PM/QA-агентам… нужен доступ к `apps/api`… новая запись в сетевом allowlist»).

**Решение архитектора: доступ не открывается.** Вместо него используется приём, уже проверенный в [EPIC-011](EPIC-011-executor-roles.md) для роли Reviewer: агент записывает свой результат в файл в песочнице, Orchestrator читает его и применяет **через Application Layer**. Тогда:

- агент физически не может вызвать ни `plan`, ни `complete-testing` — `apps/api` из песочницы недостижим, как и раньше;
- контрольные точки остаются недоступными агенту **структурно**, а не по договорённости;
- переходы по-прежнему совершает платформа, что соответствует контракту Executor ([ADR-005](../adr/ADR-005-executor-contract.md)) и [ADR-014](../adr/ADR-014-module-interaction.md) («исполнитель не обращается к хранилищам платформы»).

Это **уточнение технического подхода ADR-007, а не отмена её решения**: решение — «обе роли агенты, человек подтверждает на контрольных точках» — исполняется полностью. Предположение о необходимости доступа к API оказалось излишним, потому что EPIC-011 нашёл более дешёвый и безопасный механизм передачи результата. Сетевой allowlist остаётся без изменений.

### Что именно делают роли

| Роль | Событие | Что готовит | Кто решает |
| --- | --- | --- | --- |
| Project Manager | `TaskCreated` (задача в Backlog) | Предложение Definition of Ready: scope и критерии приёмки | Человек принимает DoR (контрольная точка) |
| QA Engineer | Задача вошла в Testing | Отчёт о проверке: что проверено, что нашлось | Человек принимает приёмочное решение (контрольная точка) |

Обе роли **оставляют задачу в её состоянии**: PM не переводит Backlog → Ready, QA не переводит Testing → Done. Автоматика доводит задачу до контрольной точки и останавливается — ровно то, что [`workflow.md`](../architecture/workflow.md#контрольные-точки-человека) описывает нормативно.

### Найденное следствие: проекция сейчас игнорирует уточнение полей

`TaskProjection` заполняет `Title`/`Type`/`Scope`/`AcceptanceCriteria` **один раз** из `TaskCreated` и намеренно не меняет их дальше — в комментарии прямо сказано, что ни одно последующее событие их не пересматривает, потому что `SetScope`/`SetAcceptanceCriteria` домена вызываются только внутри `CreateTask`.

PM-агент это нарушает: он уточняет scope и критерии **уже существующей** задачи в Backlog. Значит нужны событие об уточнении и его применение в проекции — иначе человек в Dashboard увидит исходную задачу без того, что подготовил PM, и примет DoR не глядя на результат работы агента. Дефект был бы неотличим от «агент ничего не сделал».

Доменная сторона к этому готова: `SetScope`/`SetAcceptanceCriteria` **разрешены только в Backlog** (`ErrNotBacklog`) — то есть домен уже выражает «уточнять можно, пока задача не принята». Не хватает use-case в Application Layer.

## Scope

### Входит

- **`internal/application`** — use-case уточнения задачи в Backlog (scope и/или критерии приёмки) поверх уже существующих доменных команд; публикует событие об уточнении.
- **`internal/application/projection.go`** — применение этого события к `TaskView`; снятие нынешнего допущения «описательные поля не меняются после создания».
- **`agents/claude-code`** — инструкции для ролей `project-manager` и `qa` (сейчас — `ErrUnsupportedRole`); конвенция файлов результата: предложение DoR и отчёт проверки. Один адаптер и один образ на все роли (ADR-007).
- **`apps/orchestrator`** — диспетчеризация PM на `TaskCreated` и QA на вход задачи в Testing; применение результатов через Application Layer; бутстрап исполнителей обеих ролей.
- **Отчёт QA записывается как Artifact** — у платформы для этого уже есть `ResultService`; отчёт это свидетельство выполненной работы, в отличие от вердикта ревью (решение о работе).
- **`apps/api`/`apps/dashboard`** — показать человеку то, что подготовил агент, рядом с решением, которое он принимает: уточнённые scope/критерии и отчёт QA. Без этого автоматизация ролей не даёт человеку ничего.
- Документация: `workflow.md`, `orchestrator.md`, README адаптера и Orchestrator'а, `docs/api/`.
- Живая проверка на реальной инфраструктуре и закрытие эпика.

### Не входит

- **Доступ агентов к `apps/api` и изменение сетевого allowlist** — решение выше: не требуется, и открывать не следует.
- **Автоматическое прохождение контрольных точек** — прямо запрещено ADR-007; PM и QA останавливаются перед ними.
- **Аутентификация** — остаётся отложенной (ADR-012).
- **Эскалация ревью к человеку** (ADR-008) — отдельный вопрос, не входит.
- **Оценка качества работы агентов** — предмет живой эксплуатации, а не этого эпика.

## Критерии завершения

- [x] Агенты по-прежнему **не имеют** доступа к `apps/api`: allowlist остался `github.com`/`api.github.com`/`api.anthropic.com`. **Проверено фактически**, а не по конфигурации: контейнер во внутренней сети песочницы не смог достучаться до API (`000`, нет маршрута). Плюс тест, что ни один промпт не упоминает платформенный API.
- [x] PM-агент уточняет scope и критерии приёмки задачи в Backlog; результат виден человеку — TASK-096/098/100.
- [x] QA-агент готовит отчёт проверки; отчёт записывается как `TestReport` и виден человеку — TASK-099/100.
- [x] **Ни одна роль не проходит контрольную точку** — закреплено тестами (подсчёт `TaskPlanned`/`TestsPassed` = 0 во всех путях) и **подтверждено вживую**: после работы PM задача в Backlog с нулём `TaskPlanned`, после работы QA — в Testing с нулём `TestsPassed`/`MergeCompleted`/`TaskCompleted`.
- [x] Уточнение описательных полей доезжает до `TaskView` и выживает пересборку проекции из журнала — TASK-096.
- [x] Неудача агента любой роли не двигает задачу и не подменяет результат выдуманным — тесты по всем ролям; **подтверждено вживую на всех четырёх ролях сразу**: каждая упала без ключа провайдера, и ни одна не сдвинула задачу и не записала заглушку.
- [x] Подтверждено вживую на реальной инфраструктуре (PostgreSQL + Docker + настоящий приватный репозиторий и действительный токен) — TASK-101; ограничение по `ANTHROPIC_API_KEY` зафиксировано ниже.
- [x] Документация и PROJECT_MANIFEST/PROJECT_HEALTH/ROADMAP/CHANGELOG синхронизированы — TASK-101.

## Риски и зависимости

- **Самый вероятный способ испортить эпик — дать агенту доступ к `apps/api` «для удобства».** Это снимет единственную реальную защиту контрольных точек (аутентификации нет) и позволит агенту самому принять DoR и вынести приёмочное решение — прямо противоположное замыслу ADR-007. Приём с файлом результата уже проверен на роли Reviewer и достаточен.
- **Допущение проекции о неизменности описательных полей снимается** — это касается уже закрытого EPIC-004. Изменение точечное (новое событие + его применение), но затрагивает read-модель, на которую опираются Dashboard и Orchestrator; проверка пересборки из журнала обязательна.
- **Качество работы PM/QA-агентов платформа проверить не может.** Плохо подготовленный DoR или пустой отчёт QA — это то, что увидит человек в контрольной точке; в этом и смысл того, что точки остались человеческими. Автоматизация здесь снижает объём рутины, а не ответственность.
- **Наследуется ограничение EPIC-006/010/011:** без `ANTHROPIC_API_KEY` содержательная работа агента любой роли вживую не проверяется — подтверждается только механика.
- **Слежение по-прежнему синхронное** (EPIC-010): с четырьмя ролями цикл опроса простаивает дольше. Причина та же — доменная модель не отслеживает занятость исполнителя; признак занятости остаётся доменным решением.
- Зависит от: EPIC-010 (диспетчеризация и слежение), EPIC-011 (role-aware промпты, приём с файлом результата), EPIC-012 (контрольные точки видимы и действенны), ADR-007, ADR-012.

## Результат

Все четыре роли автоматизированы, и платформа **останавливается перед каждой контрольной точкой человека**. PM уточняет задачу в Backlog, Developer пишет код и открывает Pull Request, Reviewer выносит вердикт, QA готовит отчёт — а приём Definition of Ready и приёмочное решение остаются человеку. Это не незавершённость, а исполнение [ADR-007](../adr/ADR-007-pm-qa-executors.md).

**Главное решение эпика сняло риск, а не смягчило его.** ADR-007 предполагала дать PM/QA-агентам доступ к `apps/api`; EPIC-012 показал, что это убрало бы единственную реальную защиту контрольных точек. Вместо доступа применён приём, проверенный на роли Reviewer: результат передаётся файлом, применяет его платформа. Агент физически не может вызвать ни `plan`, ни `complete-testing` — **проверено фактически**: контейнер во внутренней сети песочницы не достучался до API.

**Сквозной прогон вживую** (реальный PostgreSQL, Docker, приватный репозиторий, действительный токен) прошёл весь путь: задача → PM → приём DoR человеком → Developer → ревью → QA → приёмочное решение человека → **настоящий Pull Request слит в GitHub** и задача в Done с порядком событий по ADR-008. Обе контрольные точки подтверждены **отрицательными** проверками: после PM ноль `TaskPlanned`, после QA ноль `TestsPassed`/`MergeCompleted`/`TaskCompleted`. Перезапуск `apps/api` посреди сценария состояние не потерял.

**Все четыре агента упали без `ANTHROPIC_API_KEY` — и ни один не сдвинул задачу и не записал заглушку.** Это оказалось самой ценной частью прогона: отказ каждой роли проверен на настоящей инфраструктуре, а не только на фейках.

## Open Questions

1. **Содержательная работа агентов вживую не проверена** — `ANTHROPIC_API_KEY` в этой среде отсутствует. Проверена вся механика (диспетчеризация, песочница, чтение результатов, применение через Application Layer, остановки на контрольных точках) и все отказные пути; не проверено качество самих предложений, вердиктов и отчётов. Ограничение наследуется с EPIC-006 и остаётся единственным непройденным участком v1.0.
2. **Один исполнитель на роль**, идентификатор выведен из роли — доверенная однопользовательская установка (ADR-012). Масштабирование требует признака занятости в спецификации Executor.
3. **Слежение синхронное** — с четырьмя ролями цикл опроса простаивает дольше; причина та же доменная.
4. **Pull Request не записывается как Artifact** (спецификация это предусматривает) и **артефакты читаются через API лишь частично** — оба вопроса открыты с EPIC-012.
