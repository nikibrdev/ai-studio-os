# Стратегия тестирования

## Назначение

Определяет уровни тестирования и требования к тестам в AI Studio OS, а также как прогнать каждый уровень локально.

## Содержание

### Уровни тестирования

| Уровень | Что проверяет | Инструменты |
| --- | --- | --- |
| Unit | Доменная логика в изоляции | `go test` (Go), Vitest + React Testing Library (`apps/dashboard`, [ADR-009](../adr/ADR-009-toolchain.md)) |
| Интеграционные | Взаимодействие модулей и инфраструктуры (PostgreSQL, Qdrant) | `go test -tags=integration` + `docker compose` |
| End-to-End | Пользовательские сценарии через интерфейс | Playwright |

### Как прогнать локально

**Unit-тесты** — без внешних зависимостей, входят в `make verify`:

```bash
make test                      # Go
cd apps/dashboard && pnpm test # frontend
```

**Интеграционные тесты** — за build-тегом `integration`, требуют поднятых хранилищ:

```bash
docker compose up -d
TEST_DATABASE_URL="postgres://ai_studio_os:ai_studio_os@localhost:5432/ai_studio_os?sslmode=disable" \
  TEST_QDRANT_URL="http://localhost:6333" \
  go test -tags=integration -count=1 ./...
```

**Переменные называются `TEST_DATABASE_URL`/`TEST_QDRANT_URL`, а не `DATABASE_URL`/`QDRANT_URL`** — так тест не может случайно отработать на базе запущенного приложения. Цена этого разделения: при неверном имени переменной тесты **молча пропускаются**, а `go test` печатает `ok` по каждому пакету — вывод выглядит зелёным, хотя не выполнено ничего (обнаружено живой проверкой установки, TASK-105). Признак пропуска — неправдоподобно малое время прогона; надёжнее прогонять с `-v` и убеждаться в отсутствии `SKIP`. Те же значения задаёт CI ([verify.yml](../../.github/workflows/verify.yml), job `integration`).

`-count=1` отключает кэш результатов: интеграционный тест зависит от внешнего состояния, и закэшированный `ok` о нём ничего не говорит.

### Требования

1. Тестируемость закладывается в дизайн: зависимости — через интерфейсы, подмена — без монки-патчинга и магии.
2. Критическая бизнес-логика покрывается unit-тестами обязательно.
3. Тест читается как спецификация: имя описывает сценарий и ожидание.
4. Тесты детерминированы: без зависимости от времени, сети и порядка выполнения.
5. Интеграционные тесты используют реальные зависимости в контейнерах, а не моки инфраструктуры.
6. Тесты — часть Definition of Done (действует с v0.4 Application Layer).
7. Инфраструктурный фейк должен вести себя как реальная зависимость в том, что тест утверждает. Фейк, игнорирующий переданную команду, доказывает разбор вывода, но не то, какая команда выполняется, — так пропущен [BUGFIX-007](../../tasks/done/BUGFIX-007-artifacts-reports-inherited-history.md).

### Роль QA Engineer

QA Engineer (человек или агент) проверяет соответствие результата критериям приёмки, полноту тестов и прогоняет end-to-end сценарии. Обязанности роли: [.claude/agents/qa.md](../../.claude/agents/qa.md).

### Осознанно не определено

- **Целевые пороги покрытия не заданы.** Покрытие измеряется (`go test -cover`), но числового порога в `make verify` нет: порог проверяет объём тестов, а не их содержательность, и в проекте, где тесты пишет агент, поощрял бы ровно не то поведение. Требование содержательности задаёт правило 3 и обязательная проверка инвариантов таблицей тестов.
- **Отдельных тестовых окружений нет.** Интеграционные тесты работают на том же `docker compose`, что и локальная разработка; полноценное тестовое окружение появится при первой установке вне машины разработчика.
