# agents/claude-code — адаптер Claude Code

## Назначение

Первый реальный адаптер `platform.Executor` ([ADR-005](../../docs/adr/ADR-005-executor-contract.md)): исполняет роль Developer через Claude Code, запущенный внутри изолированного Docker-контейнера ([ADR-006](../../docs/adr/ADR-006-agent-execution-environment.md)).

### `Executor` — реализация `platform.Executor`

`New(image, gitToken, providerAPIKey)` (TASK-055) создаёт одно значение `Executor` на один жизненный цикл Execution (`Accept` → ... → `Finish`) — не переиспользуется между несколькими исполнениями.

- **`Accept`** — собирает промпт из полей `platform.ExecutorTask` (роль, заголовок, тип, scope, критерии приёмки) и запускает песочницу (`container.Manager.Start`) с командой `claude --print --permission-mode bypassPermissions <промпт>`. `--permission-mode bypassPermissions` необходим для запуска без человека (некому отвечать на запрос подтверждения инструмента внутри контейнера) — это ровно та граница, ради которой существует песочница TASK-054 (allowlist сети, отсутствие секретов платформы, эфемерная рабочая копия). Точное поведение флагов CLI подтверждается реальным вызовом в TASK-056 — эта задача проверяет только логику адаптера (на фейковой песочнице), не настоящий вызов AI-провайдера.
- **`Artifacts`** — возвращает коммиты, произведённые **этим** исполнением, как `platform.Artifact{Type: "Commit"}`; открытие Pull Request'а — задача вызывающего application-сервиса (`ResultService`/`CompletionService`, EPIC-004, через `platform.RepositoryProvider`), не этого адаптера. Диапазон ограничен явно: при клонировании фиксируется `HEAD` (`container.BaseSHAFile`), и запрашивается `git log <base>..HEAD` ([BUGFIX-007](../../tasks/done/BUGFIX-007-artifacts-reports-inherited-history.md)). До этого исправления выполнялся `git log` без диапазона, то есть возвращалась вся унаследованная от базовой ветки история — на любом репозитории с коммитами чужая работа записывалась как произведённая этим исполнением (`Origin: produced`) и по ней открывался Pull Request. Пустой диапазон (агент ничего не закоммитил) — корректный пустой результат; отсутствующий базовый SHA означает, что клон не завершился, и это ошибка.
- **`Status`** — отображает состояние контейнера (`container.Manager.Status`) на `running`/`succeeded`/`failed`.
- **`Finish`** — останавливает песочницу (`container.Manager.Stop`).

`sandbox` — узкий интерфейс, сужающий `*container.Manager` до четырёх нужных адаптеру методов (тот же паттерн, что `commandRunner` в `container/`) — тесты подставляют фейк, не требуют реального Docker (91.1% покрытия).

### `container` — жизненный цикл Execution

`Manager` (TASK-054) управляет Docker-контейнером Execution через прямые вызовы `docker` CLI (`os/exec`) — без клиентской библиотеки Docker: `agents/` не может импортировать `internal/infrastructure`, а горстка команд (`run`, `network create`, `exec`, `rm`) не оправдывает новую зависимость (тот же принцип, что ADR-017 и GitHub-адаптер).

**Сетевой allowlist** — по ADR-006: две Docker-сети на Execution — внутренняя (`--internal`, без маршрута наружу) и обычный `bridge` (с интернетом). Контейнер исполнения подключён только к внутренней сети; прокси-контейнер (`ubuntu/squid` — существующий публичный образ, не собственная сборка, тот же принцип, что `postgres:16-alpine` для БД) подключён к обеим и разрешает `CONNECT`/HTTP только к доменам allowlist'а (по умолчанию — `github.com`/`api.github.com`, плюс явно переданные), остальное — `deny all`. У контейнера исполнения физически нет иного пути наружу, кроме как через прокси.

**Секреты** — git-токен и ключ AI-провайдера передаются только переменными окружения контейнера (`GIT_TOKEN`, `ANTHROPIC_API_KEY`). Токен не встраивается в URL клонирования и не передаётся флагом (оба способа оставляют секрет в списке процессов контейнера, видном через `docker inspect`/`ps`) — вместо этого генерируется `GIT_ASKPASS`-скрипт, читающий токен из переменной окружения `git`'ом самостоятельно.

**Рабочая копия** — клонируется командой `git clone --branch <branch>` внутри контейнера при старте (в `/workspace/repo`); уничтожается вместе с контейнером при `Stop` (ADR-006: эфемерна на всё время Execution, не дольше).

**Формат идентификатора репозитория ([BUGFIX-006](../../tasks/done/BUGFIX-006-container-clone-url-doubled-host.md)).** Платформа передаёт его в каноническом хранимом виде `<host>/<owner>/<name>` ([`platform.RepositoryProvider`](../../internal/platform/repository.go)), а URL клонирования подставляет хост сам — поэтому `normalizeRepository` снимает схему, хост и суффикс `.git` и **проверяет**, что осталось ровно два непустых сегмента; неразбираемое значение отвергается до запуска контейнера. До этого исправления хост удваивался (`https://github.com/github.com/owner/name.git`), и **любое** реальное исполнение падало с `exit code 128` — сообщением, которое ничего не говорило о причине. Дефект был невидим, потому что тесты этого пакета подавали краткую форму `org/repo`; нашёлся первым сквозным живым прогоном (TASK-085). Тот же класс дефекта, что [BUGFIX-005](../../tasks/done/BUGFIX-005-github-repo-identifier-format.md) в GitHub-адаптере.

**Контейнер не завершается сразу после команды** — обнаружено реальным прогоном (TASK-056): `docker exec` работает только с запущенным контейнером, а Docker считает контейнер завершённым, как только выходит его главный процесс. Если команда (например, Claude Code) падает быстро, окна между «команда завершилась» и «`docker exec` уже не работает» не остаётся вовсе — `Artifacts`/`Exec` физически не успевают ничего собрать. Исправлено: после клонирования и команды контейнер записывает код возврата в файл (`exitCodeFile`) и засыпает на 300 секунд вместо немедленного выхода; `Status` читает этот файл (а не `docker inspect .State.Running`, который теперь всегда true, пока идёт этот сон) — `Exec` также явно указывает рабочую директорию (`--workdir /workspace/repo`), так как `WORKDIR` образа (TASK-053) — родительский каталог, не сам клон.

### Тестирование

Юнит-тесты (`lifecycle_test.go`, `proxy_test.go`) не требуют реального Docker: пул команд сужен до интерфейса `commandRunner`, тесты подставляют фейк — проверяют построение команд, порядок операций, откат при ошибке, что секреты не попадают в аргументы команд.

Интеграционный тест (`lifecycle_integration_test.go`, тег `integration`) требует реальный Docker и собранный образ `docker/execution` (TASK-053); пропускается, если не задана `TEST_DOCKER` (тот же паттерн, что `TEST_DATABASE_URL` в `internal/infrastructure` — тест создаёт настоящие Docker-ресурсы, включение по явному согласию):

```bash
docker build -t ai-studio-os-execution -f docker/execution/Dockerfile .
export TEST_DOCKER=1
go test -tags=integration ./agents/claude-code/container/...
```

Прогнан вживую (TASK-054): реальное клонирование `nikibrdev/ai-studio-os`, обращение к `api.github.com` (в allowlist'е — успех) и к `example.com` (не в allowlist'е — заблокировано), три прогона подряд стабильны.

Полный жизненный цикл `Executor.Accept → Status → Artifacts → Finish` прогнан вживую целиком (TASK-056, реальный Docker, реальное клонирование `nikibrdev/ai-studio-os`, без ключа AI-провайдера — см. `docs/roadmap/EPIC-006-ai-agent-runtime.md` и отчёт TASK-056 про открытый вопрос с секретом): `Status` корректно доходит до `failed` (реальный `claude` без учётных данных завершается с ненулевым кодом), `Artifacts` читает коммиты из уже остановившей выполнение, но ещё не удалённой рабочей копии, `Finish` корректно освобождает все ресурсы. Прогнано дважды подряд, без утечек контейнеров/сетей.

**Уточнение к этому прогону (BUGFIX-007).** Тогда «`Artifacts` успешно читает историю коммитов» было записано как успех — а это и было проявлением дефекта: читалась унаследованная история клонированного репозитория, а не результат исполнения (агент без ключа провайдера не коммитил ничего). Дефект стал очевиден только при сквозной проверке EPIC-010/TASK-085 на репозитории, где чужой коммит был единственным. Проверено после исправления вживую внутри образа исполнения: до коммита агента диапазон пуст, после одного коммита возвращается только он, тогда как прежняя команда без диапазона вернула бы и его, и унаследованный `Initial commit`.

**Первая сквозная проверка вживую с реальным репозиторием и токеном** (EPIC-010/TASK-085) нашла в этом пакете два дефекта, невидимых для юнит-тестов: [BUGFIX-006](../../tasks/done/BUGFIX-006-container-clone-url-doubled-host.md) (удвоенный хост в URL клонирования — **любое** исполнение падало с `exit 128`) и BUGFIX-007 выше. Оба существовали с EPIC-006 и не проявлялись, потому что тесты подавали данные в форме, отличной от той, которую реально передаёт платформа.
