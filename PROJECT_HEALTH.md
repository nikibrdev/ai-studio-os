# PROJECT_HEALTH — прогресс проекта

## Назначение

Состояние проекта одним взглядом: экспертная оценка готовности по направлениям. Обновляется вместе с [PROJECT_MANIFEST.md](PROJECT_MANIFEST.md); со временем показатели будут выводиться из [engineering/metrics/](engineering/metrics/).

| Implementation | **98%** | **Все четыре роли автоматизированы** (EPIC-010…013): PM уточняет задачу, Developer пишет код и открывает PR, Reviewer выносит вердикт, QA готовит отчёт — и платформа **останавливается перед обеими контрольными точками человека** (приём DoR, приёмочное решение), что подтверждено вживую отрицательными проверками. Контрольные точки видимы и действенны (EPIC-012): `GET /decisions` и первый мутирующий UI в `apps/dashboard`. Агенты структурно не достают до `apps/api` — проверено фактически. Без auth (ADR-012, доверенная установка). **Не пройдено вживую**: содержательная работа агентов — нет `ANTHROPIC_API_KEY` (честный предел с TASK-056); проверена вся механика и все отказные пути. Остаётся пятый пункт v1.0 — стабилизация и релиз |
| Testing | **60%** | 409 функций-тестов Go плюс 11 подтестов (`go test` + `t.Run`; метод подсчёта указан явно — у прежней цифры он не был зафиксирован, поэтому сравнивать их напрямую нельзя) (Domain 91.1–100%, Application 83.7%/88.4%, Infrastructure — юнит-часть 3.5–90% + интеграционные на реальном PostgreSQL/Qdrant, Agent Runtime — юнит-часть 84–91% + интеграционный тест на реальном Docker, API — `httpapi` 85.1% + сквозной HTTP-тест на реальном PostgreSQL, Orchestrator 75.4%, `agents/claude-code` 92.5%) + 8 unit-тестов `apps/dashboard` (Vitest); CI-job `integration` (Postgres + Qdrant сервис-контейнеры), CI-job `verify` включает `apps/dashboard` (TASK-077); e2e/QA Engine — по решению архитектора, не раньше v1.0. **Урок EPIC-010:** четыре дефекта (BUGFIX-004…007) прошли через 200+ тестов, потому что каждая сторона шва тестировалась своими данными — сквозная живая проверка с реальными внешними системами нужна в каждом интегрирующем эпике, а не только в последнем |
| API | **100%** | REST реализован (ADR-003, EPIC-008/009/012): весь golden path, списковые операции и `GET /decisions` (контрольные точки) через `apps/api`; read-модель восстанавливается из журнала при старте (BUGFIX-010); без auth (ADR-012, Вариант 1) |
| Dashboard | **100%** | Реализован: read-only наблюдение (EPIC-009) плюс запись в контрольных точках (EPIC-012) — раздел «Ждут решения» и подтверждение обоих решений через Server Actions, первый мутирующий UI в проекте, подтверждён в реальном браузере; произвольное редактирование/auth/realtime — сознательно отложены |
| Orchestrator | **90%** | Реализован (EPIC-010/011): курсорный опрос журнала, бутстрап исполнителей, диспетчеризация **двух** ролей (Developer на `TaskPlanned`, Reviewer на `ReviewRequested`), слежение за исполнением, применение вердикта ревью, гарантированный `Finish`; подтверждено вживую на реальной инфраструктуре. Выбор исполнителя исправлен (TASK-086): запись реестра и запущенный бэкенд согласованы по построению, посторонние записи выбор не меняют — проверено вживую. Не 100%: содержательные исходы (коммиты агента → Pull Request → Review; применение вердикта) вживую не пройдены — нет ключа провайдера, покрыты юнит-тестами; PM/QA сознательно не диспетчеризуются (их выходы — контрольные точки человека, ADR-007) |

### Методика

Оценки — экспертные, относительно scope соответствующего направления в MVP (v1.0). Правила округления не формализованы; спорные изменения оценок обсуждаются на ревью. Автоматизируемые показатели (задачи, пакеты, покрытие документацией) — в снимках [engineering/metrics/](engineering/metrics/).
