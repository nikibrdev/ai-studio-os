# apps/orchestrator — координатор процесса

## Назначение

Координатор ([EPIC-010](../../docs/roadmap/EPIC-010-orchestrator.md), v1.0): реагирует на события жизненного цикла задачи и сам запускает исполнителей через контракт Executor — без участия человека в рутинном шаге «взять задачу в работу». Доменных правил и durable-состояния не содержит ([module-boundaries.md](../../docs/architecture/module-boundaries.md)): решения о допустимости переходов принимают модули `task`/`workflow`, вызываемые только через `internal/application`.

Полное архитектурное описание механизма — [docs/architecture/orchestrator.md](../../docs/architecture/orchestrator.md).

### Зависимости (module-boundaries.md)

- **Разрешено:** `internal/application` (use-case-сервисы, проекция, порт `EventJournal`); `internal/infrastructure/wiring` (только в `main.go`, для сборки `System`); контракт `platform.Executor`; `pkg/`; стандартная библиотека.
- **Запрещено:** доменные правила (решения о допустимости переходов — у модулей `task`/`workflow`); хранение доменного состояния; прямой доступ к хранилищам в обход `internal/application`; зависимость от `apps/api`.
- **Узкое исключение:** `main.go` как composition root импортирует конкретный адаптер `agents/claude-code`, чтобы его создать — сконструировать реализацию должен кто-то. `Dispatcher` при этом знает только `platform.Executor`: адаптер приходит через поле-фабрику `NewExecutor func() (platform.Executor, error)` и в логике диспетчеризации не назван. То же разделение, что в `apps/api`, где `main.go` знает инфраструктуру, а `httpapi` — нет.

### Диспетчеризация Developer (TASK-082)

На событие `TaskPlanned`:

1. Прочитать представление задачи из `TaskProjection` (заголовок, тип, scope, критерии приёмки).
2. Выбрать Active-исполнителя с ролью Developer (`ExecutorStore.List`, фильтр в памяти; `List` упорядочен по id, поэтому выбор детерминирован).
3. Определить репозиторий — первый подключённый к проекту.
4. `WorkService.StartTask` — переход Ready → In Progress и создание Execution **через Application Layer**, а не в обход state machine.
5. `RepositoryProvider.CreateBranch` — ветка `feature/<task-id>-<slug>` от `main` ([git-workflow.md](../../docs/development/git-workflow.md)). Ветка создаётся **до** `Accept`: адаптер клонирует уже существующую ветку, а не создаёт её.
6. `platform.ExecutorTask` → `Executor.Accept`.

**Slug имени ветки.** Заголовки задач в проекте русские, а наивный ASCII-slug из русского заголовка пуст. Вместо выдуманной таблицы транслитерации в этом случае используется просто `feature/<task-id>` — этого достаточно: `TASK-NNN` уникален в рамках проекта ([ADR-011](../../docs/adr/ADR-011-task-identifiers.md)).

**Наполнение проекции.** Orchestrator не подписан на шину `apps/api` (она внутрипроцессная), поэтому свою `TaskProjection` он наполняет из журнала: `Poller.Seed` применяет историю при старте, `Dispatcher.Observe` — каждое новое событие, до диспетчеризации. Без истории у задачи, созданной до запуска процесса и запланированной после, не было бы ни заголовка, ни scope (этот путь чтения — единственный, [ADR-014](../../docs/adr/ADR-014-module-interaction.md)).

### Слежение за исполнением (TASK-083)

После `Accept` управление не возвращается в цикл, пока исполнение не завершится:

1. Опрос `Executor.Status` с интервалом `statusPollInterval` (10с) до терминального состояния, с общим таймаутом `executionTimeout` (30 мин) — предохранитель от зависшей песочницы.
2. При успехе: `Executor.Artifacts` → на каждый коммит `RecordDraftArtifact` + `PublishArtifact` → `OpenPullRequest` → `SucceedExecution` → `CompletionService.RequestReview` (задача переходит в Review).
3. При неудаче, таймауте или ошибке на любом шаге до `SucceedExecution` — `FailExecution`.
4. `Executor.Finish` вызывается **всегда**, через `defer`: эфемерная рабочая копия умирает вместе с контейнером ([ADR-006](../../docs/adr/ADR-006-agent-execution-environment.md)).

Артефакты записываются **до** `SucceedExecution`: прикрепить артефакт можно только к Execution в состоянии Running (доменный инвариант), после `Succeed` он уже не Running.

**Поведение при отказе на каждом шаге** — проработано заранее, а не обнаружено вживую (урок TASK-082):

| Шаг | Отказ | Что делаем | Состояние после |
| --- | --- | --- | --- |
| Опрос `Status` | Транзиентная ошибка | Логируем, повторяем до таймаута | Execution Running |
| Опрос `Status` | Таймаут | `FailExecution` | Execution Failed, Task In Progress |
| `Artifacts` | Ошибка `git log` | `FailExecution` | Execution Failed, PR нет |
| `RecordDraftArtifact`/`PublishArtifact` | Ошибка домена | `FailExecution` | Execution Failed, часть артефактов записана |
| `OpenPullRequest` | GitHub недоступен | `FailExecution` | Execution Failed, артефакты записаны |
| `RequestReview` у провайдера | Не удалось прокомментировать PR | Логируем, продолжаем | PR открыт — это главное |
| `Finish` | Контейнер уже удалён | Логируем | Исход работы не меняется |

**Задача при провале исполнения остаётся In Progress.** `ExecutionFailed` не переводит Task — ни в state machine, ни в проекции. Это существующий доменный дизайн, а не потерянный здесь переход: вернуть задачу в работу — решение человека через `apps/api`. Закреплено тестом.

**Успех без коммитов — не ошибка.** Открывать Pull Request нечему, но Execution всё равно завершается успешно и задача уходит в Review, где человек увидит, что ничего не произведено.

### Переменные окружения

- `DATABASE_URL` — DSN PostgreSQL, обязателен ([`postgres.DatabaseURLEnv`](../../internal/infrastructure/postgres/config.go)).
- `QDRANT_URL` — опционален; пустое значение оставляет `wiring.System.Memory` равным `nil` (тот же принцип, что в `apps/api`).
- `EXECUTION_IMAGE` — образ песочницы исполнения (ADR-006); по умолчанию `ai-studio-os-execution` — имя, которое собирает [agents/claude-code](../../agents/claude-code/README.md).
- `GITHUB_TOKEN` — токен для git-операций внутри песочницы ([`github.TokenEnv`](../../internal/infrastructure/github/provider.go)).
- `ANTHROPIC_API_KEY` — ключ AI-провайдера. **Пустое значение допустимо**: песочница всё равно запустится, но реального вызова провайдера не будет — так проверяется механика контейнера без реального ключа (Open Question TASK-056). При пустом значении процесс печатает предупреждение, а не падает.
- `POLL_INTERVAL` — период опроса журнала; по умолчанию `5s`. Должен быть положительным.

### Почему опрос журнала, а не подписка

Продуктивная `eventbus.Bus` ([ADR-002](../../docs/adr/ADR-002-event-delivery.md)) доставляет события только подписчикам **своего процесса**: `Subscribe` регистрирует обработчик в памяти. `apps/api` и `apps/orchestrator` — разные процессы, поэтому подписаться на шину `apps/api` физически невозможно. Orchestrator опрашивает журнал событий (`event_journal`) по курсору через порт `application.EventJournal` — временный, явно объявленный шаг между «только in-process» и настоящей шиной сообщений (Redis Streams/NATS, будущий шаг самой ADR-002).

**Курсор — по монотонной последовательности вставки (`seq`), не по времени.** `OccurredAt` штампуется доменом до записи строки, поэтому курсор по времени бесшумно перешагивает события, ставшие видимыми «в прошлом» (подробно — [TASK-080](../../tasks/done/TASK-080-event-journal-since.md), миграция 0007).

### Ограничения этой версии

- **Курсор хранится в памяти процесса.** Перезапуск возобновляет чтение с вершины журнала: события, случившиеся во время простоя, пропускаются (задача останется в Ready, пока её не запустят вручную через `apps/api`). Принятый риск v1.0 — операционно видимый, в отличие от бесшумной потери. С курсором по `seq` устойчивое хранение — это одно целое число, если потребность появится.
- **Один Developer-исполнитель**, идентификатор фиксирован (`executor-claude-code-developer`) — именно он и обеспечивает идемпотентность повторного запуска. Масштабирование на несколько исполнителей одной роли — не в этой версии.
- **Ошибка обработчика не останавливает цикл, курсор всё равно сдвигается.** Иначе одно необрабатываемое событие заблокировало бы все последующие. Задача остаётся в текущем состоянии, её можно провести вручную через `apps/api`. Повторные попытки (retry) сознательно не входят в EPIC-010.
- **Слежение синхронное: пока идёт исполнение, цикл не обрабатывает другие события** — включая события других проектов. Альтернатива (горутина на исполнение) отвергнута осознанно: доменная модель не отслеживает занятость исполнителя (`AvailableForAssignment` — это только «Active ли он»), поэтому два `TaskPlanned` подряд назначили бы работу одному и тому же бэкенду параллельно. Синхронность выстраивает работу в очередь, что соответствует ограничению «один исполнитель на роль». Признак занятости — доменное решение (изменение спецификации Executor), а не то, что стоит изобретать здесь.
- **Исполнитель в состоянии Retired не переиспользуется** — процесс сообщает об ошибке, а не регистрирует замену под новым идентификатором: это оставило бы две записи и переопределило бы решение оператора вывести бэкенд из эксплуатации.
