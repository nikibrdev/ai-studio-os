# apps/dashboard — веб-интерфейс

## Назначение

Веб-интерфейс на Next.js 15 ([EPIC-009](../../docs/roadmap/EPIC-009-dashboard.md), v0.8): наблюдение за проектами и задачами. Работает исключительно через `apps/api` ([module-boundaries.md](../../docs/architecture/module-boundaries.md)) — без прямого обращения к `internal/`, БД или шине событий.

Первая версия (EPIC-009) была read-only. С [EPIC-012](../../docs/roadmap/EPIC-012-human-checkpoints.md) появилась запись — но **только контрольные точки человека** (приём Definition of Ready и приёмочное решение): произвольное редактирование задач и создание проектов из UI по-прежнему не предусмотрены. Без аутентификации (ADR-012, Вариант 1), без канала реального времени (см. EPIC-009 «Контекст»).

**Платформа не отличает человека от агента** на командах подтверждения (аутентификации нет) — гарантия процессная, подробнее в [workflow.md](../../docs/architecture/workflow.md#контрольные-точки-человека).

## Содержание

### Толчейн (ADR-009, зафиксировано при открытии EPIC-009)

Node.js 22 LTS, TypeScript, pnpm, ESLint (`next/core-web-vitals` + `next/typescript` + `prettier`) + Prettier, Vitest + React Testing Library (jsdom).

### Структура

- `src/app/layout.tsx` — корневой layout, шапка с навигацией.
- `src/app/page.tsx` — `/`, список проектов (TASK-075).
- `src/app/loading.tsx`/`error.tsx` — общее состояние загрузки (Suspense) и ошибки (Error Boundary с кнопкой «Попробовать снова») для всех страниц.
- `src/app/projects/[id]/page.tsx` — список задач проекта (TASK-076).
- `src/app/projects/[id]/tasks/[taskId]/page.tsx` — детали задачи: заголовок, тип, scope, критерии приёмки, состояние, время обновления (TASK-076).
- `src/app/decisions/page.tsx` — `/decisions`, задачи, ожидающие решения человека (TASK-093); `DecisionActions.tsx` — действия подтверждения (TASK-094).
- `src/lib/actions.ts` — Server Actions записи: приём Definition of Ready, приёмочное решение, возврат на доработку (TASK-094).
- `src/lib/api.ts` — типизированный клиент `apps/api`, типы вручную зеркалят `docs/api/*.md`, без генерации из OpenAPI.

### Контрольные точки человека

Раздел «Ждут решения» показывает задачи, стоящие в контрольных точках ([workflow.md](../../docs/architecture/workflow.md#контрольные-точки-человека)). Тип решения приходит с сервера полем `awaitingDecision` — соответствие состояния задачи и решения **не выводится здесь** из `state`: это правило платформы, и дублировать его в UI запрещено ([module-boundaries.md](../../docs/architecture/module-boundaries.md)).

Пустой список — нормальное состояние системы, а не ошибка: показывается объясняющий текст, не пустой экран.

Задачи разных проектов могут иметь одинаковый номер (`TASK-NNN` уникален только в рамках проекта — [ADR-011](../../docs/adr/ADR-011-task-identifiers.md), BUGFIX-003), поэтому список ключуется и подписывается парой «проект/задача».

### Запись: подтверждение решений (TASK-094)

Первый мутирующий UI в проекте — до него `apps/dashboard` был целиком read-only.

- **Через Server Actions** (`src/lib/actions.ts`), а не `fetch` из браузера: `apps/api` **не отдаёт CORS-заголовков**, поэтому запрос из браузера на другой порт был бы заблокирован. Server Action выполняется на сервере Next.js, который и так общается с API — CORS не возникает, адрес API остаётся серверным. Альтернатива потребовала бы добавить CORS в API ради UI.
- **Обновление данных** — `revalidatePath` при успехе (список решений, страница проекта, страница задачи). Только при успехе: после отказа состояние не изменилось, и выдавать прежнее за новое нельзя.
- **Ошибка действия возвращается значением, а не исключением.** `error.tsx` — Error Boundary для отказов **рендера**, он заменяет страницу целиком; для неудавшегося действия это неверно — человек теряет контекст. Ошибка показывается рядом с кнопкой (`role="alert"`), действие можно повторить.
- **Приёмочное решение предупреждает до нажатия**, с указанием какого именно Pull Request'а: оно сливает его в основную ветку и в рамках задачи необратимо ([workflow.md](../../docs/architecture/workflow.md#контрольные-точки-человека), ADR-008). Ссылка приходит с сервера ([BUGFIX-009](../../tasks/done/BUGFIX-009-pull-request-reference-lost.md)) — знать её клиенту не нужно.
- **Отрицательный исход** («вернуть на доработку») — та же команда с `passed=false`; новых эндпоинтов не вводилось.

### Проверка типов

`pnpm typecheck` (`tsc --noEmit`) — отдельная проверка, потому что **ни `pnpm test`, ни `pnpm build` не проверяют типы в тестах**: Vitest снимает типы, не проверяя их, а `next build` проверяет только то, что импортирует приложение. Обнаружено в TASK-093: изменение обязательного поля `TaskView` сломало типы в трёх файлах тестов, и все проверки — локальные и CI — остались зелёными. Шаг добавлен в CI.

Все страницы — `export const dynamic = "force-dynamic"`: данные всегда актуальны только на момент запроса, статическая генерация `next build` неприменима (иначе сборка зависает на `fetch` к недоступному во время сборки `apps/api` — обнаружено в TASK-075).

### Проверено вживую

Полный путь навигации (список проектов → задачи проекта → детали задачи) проверен против реального `apps/api` + PostgreSQL (Playwright, headless Chromium): данные отображаются корректно, включая кириллицу; недоступный API и несуществующие проект/задача дают читаемую ошибку (`error.tsx`), а не падение страницы.

### CI

`.github/workflows/verify.yml` — шаги `pnpm install --frozen-lockfile`/`lint`/`format:check`/`typecheck`/`test`/`build` внутри job `verify` (TASK-077, шаг проверки типов — TASK-093) — тот же единственный обязательный статус-чек ветки, что и для Go-кода.

### Запуск локально

```bash
pnpm install
export NEXT_PUBLIC_API_URL="http://localhost:8080"  # apps/api, опционально — по умолчанию localhost:8080
pnpm dev
```

Требует запущенный `apps/api` (см. [apps/api/README.md](../api/README.md)) для реальных данных.

### Проверки

```bash
pnpm lint
pnpm format:check
pnpm typecheck
pnpm test
pnpm build
```
