# TASK-082: Диспетчеризация Developer на TaskPlanned

## Тип

feature

## Эпик

[EPIC-010 Orchestrator](../../docs/roadmap/EPIC-010-orchestrator.md)

## Цель

Заставить `apps/orchestrator` реагировать на `TaskPlanned`: выбрать зарегистрированного Developer-исполнителя, перевести задачу в работу (`WorkService.StartTask`), создать ветку и запустить реального `agents/claude-code` (`Executor.Accept`). Это первая половина автоматизации Developer-шага golden path; вторая половина (слежение за исполнением до Review) — TASK-083.

## Контекст

`platform.ExecutorTask.Repository`/`Branch` — git-координаты, которые обязан подготовить вызывающий код (`agents/claude-code/README.md`: адаптер клонирует уже существующую ветку, не создаёт её). Имя ветки — по конвенции `docs/development/git-workflow.md` (`feature/<task-id>-<short-name>`). Репозиторий — берётся из `Project.Repositories()` (первый/единственный, для v1.0 самой платформы). `WorkService.StartTask` (EPIC-004) не меняется — уже принимает `ExecutorID` извне.

## Scope

### Входит

- `apps/orchestrator` — обработчик события `TaskPlanned` в цикле опроса (TASK-081): получить `Project`/`Task` по `ProjectID`/`SubjectID` события, выбрать Active Developer-исполнителя через `ExecutorStore.List`, вызвать `WorkService.StartTask`.
- `RepositoryProvider.CreateBranch` — имя ветки формируется из `TaskID` и заголовка задачи (slug), базовая ветка — `main`.
- Построение `platform.ExecutorTask{TaskID, ProjectID, Role: "developer", Title, Type, Scope, AcceptanceCriteria, Repository, Branch}` из `TaskView` (поля уже есть, TASK-076) и репозитория проекта.
- Конструирование реального `agents/claude-code.Executor` (`New(image, gitToken, providerAPIKey)`, значения — из конфигурации TASK-081) и вызов `Accept`.
- Обработка ошибок: если подходящего исполнителя нет или `Accept` возвращает ошибку — логировать и не терять событие молча (задача остаётся в `In Progress`, ручной путь через `apps/api` не заблокирован).
- Юнит-тесты на фейках (`ExecutorStore`, `RepositoryProvider`, фейковая реализация `platform.Executor`) — сценарий целиком, без реального Docker.

### Не входит

- Опрос `Status`/сбор `Artifacts`/открытие PR/`RequestReview`/`Finish` — TASK-083.
- Диспетчеризация других ролей — вне эпика.

## План реализации

1. **`poller.go` — поле `Seed Handler`.** Orchestrator обязан наполнять свою `TaskProjection` из журнала (ADR-014: проекция — единственный путь чтения Task; отдельный процесс не подписан на шину `apps/api`). `Start` уже вычитывает журнал целиком, чтобы найти вершину, — те же события надо применить к проекции, иначе у задачи, созданной до запуска и запланированной после, не будет ни заголовка, ни scope. `Seed` вызывается на исторические события (только обновление read-модели), `Handle` — на новые (обновление + побочные эффекты). Разделение именно такое, чтобы история не запускала работу заново.
2. **`dispatch.go` — `Dispatcher`:**
   - Поля: `Projects application.ProjectStore`, `Executors application.ExecutorStore`, `Work *application.WorkService`, `Views *application.TaskProjection`, `Repos platform.RepositoryProvider`, `NewExecutor func() (platform.Executor, error)` (фабрика — чтобы тесты подставляли фейк вместо реального Docker), `Log`.
   - `Observe(ctx, e)` — только `Views.Handle`; передаётся как `Seed`.
   - `Handle(ctx, e)` — `Observe`, затем на `TaskPlanned` — диспетчеризация. Порядок важен: проекция должна увидеть событие раньше, чем мы читаем из неё состояние.
   - `dispatchTaskPlanned(ctx, e)`: `Views.Get(projectID, taskID)` → выбрать Active Developer-исполнителя (`Executors.List`, фильтр `AvailableForAssignment() && HasRole(RoleDeveloper)`, первый — `List` упорядочен по id, поэтому выбор детерминирован) → `Projects.Get` для репозитория (`Repositories()[0]`) → `Work.StartTask` → `Repos.CreateBranch(repo, branch, "main")` → собрать `platform.ExecutorTask` → `NewExecutor()` → `Accept`.
   - Имя ветки — `feature/<taskID>-<slug>` по [git-workflow.md](../../docs/development/git-workflow.md); slug — из заголовка. Заголовки в проекте русские, поэтому наивный slug из ASCII-символов даст пустую строку: в этом случае имя — просто `feature/<taskID>`, без выдуманной таблицы транслитерации.
   - Отсутствие исполнителя/репозитория/представления задачи — ошибка возвращается (её логирует `Poller`, курсор сдвигается, задача остаётся в Ready и может быть запущена вручную через `apps/api`). Паники быть не должно ни при каком отсутствующем данном.
3. **`main.go`** — собрать `Dispatcher` (реальный `claudecode.New` в фабрике, `sys.Repository`), передать `Seed: d.Observe`, `Handle: d.Handle`; убрать `logHandler`.
4. **Тесты** (`dispatch_test.go`, на фейках — без Docker): успешный путь целиком (проверить `ExecutorTask`: роль, заголовок, scope, критерии, репозиторий, имя ветки; факт `CreateBranch` до `Accept`; переход задачи Ready → In Progress через реальный `WorkService` на in-memory фейках); нет Active Developer-исполнителя → ошибка, `Accept` не вызван, задача осталась в Ready; проект без репозитория → ошибка; событие не `TaskPlanned` → проекция обновлена, диспетчеризации нет; slug из русского заголовка → `feature/<taskID>`; ошибка `Accept` пробрасывается.
5. **`README.md`** — раздел про диспетчеризацию; отметить промежуточное состояние (после `Accept` контейнер не останавливается до TASK-083).
6. `make verify`; живая проверка на реальном PostgreSQL — до реального запуска Docker-песочницы (нужен собранный образ и ключ провайдера) доводить не обязательно: цель этой задачи — что до `Accept` доходит корректно собранный `ExecutorTask`; полный сквозной прогон — TASK-085.

## Отчёт о выполнении

### Задача

TASK-082 — диспетчеризация Developer-работы на событие `TaskPlanned`.

### Что сделано

- **`Poller.Seed`** — новое поле: история журнала применяется к read-моделям при старте, но **не** запускает побочные эффекты. Без этого у задачи, созданной до запуска процесса и запланированной после, не было бы ни заголовка, ни scope: Orchestrator не подписан на шину `apps/api` (она внутрипроцессная), а проекция — единственный путь чтения Task (ADR-014). Ошибка на одном историческом событии логируется и не мешает старту: потерять один факт в read-модели лучше, чем не запуститься.
- **`Dispatcher`** (`dispatch.go`): `Observe` (только обновление проекции, передаётся как `Seed`) и `Handle` (`Observe` + диспетчеризация на `TaskPlanned`). Проекция обновляется **до** диспетчеризации — из неё же читается содержание задачи.
- **Порядок шагов диспетчеризации: ветка → `StartTask` → `Accept`.** Изначально план (и epic) предполагали `StartTask` → ветка; живая проверка показала, что это плохо, см. ниже.
- **Выбор исполнителя** — первый Active с ролью Developer из `ExecutorStore.List`; `List` упорядочен по id, поэтому выбор детерминирован, а не зависит от порядка обхода карты. Фильтрация в памяти: на масштабе «один исполнитель на роль» это дешевле параметризованного запроса.
- **Репозиторий** — первый подключённый к проекту. Выбор среди нескольких потребовал бы правила, которого в домене нет (`Project.repositories` — неупорядоченное множество без «основного»), а придумать его здесь значило бы поместить доменное решение в Orchestrator.
- **Имя ветки** — `feature/<task-id>-<slug>`; при пустом ASCII-slug (все заголовки в проекте русские) — просто `feature/<task-id>`, без выдуманной таблицы транслитерации. `TASK-NNN` уникален в рамках проекта (ADR-011), поэтому этого достаточно.
- **`main.go`** — сборка `Dispatcher`; **отказ стартовать без `GITHUB_TOKEN`**: без `RepositoryProvider` каждая диспетчеризация всё равно упала бы, и явная ошибка при запуске понятнее, чем ошибка на каждом событии. Пустой `ANTHROPIC_API_KEY` при этом остаётся допустимым — он влияет только на то, что происходит **внутри** песочницы (и это специально проверяемый сценарий, TASK-056), тогда как провайдер репозитория нужен самому Orchestrator'у до её запуска.
- **`module-boundaries.md`** — зафиксировано узкое исключение: `main.go` как composition root импортирует конкретный `agents/claude-code`, чтобы его создать; `Dispatcher` знает только `platform.Executor` (адаптер приходит через поле-фабрику `NewExecutor`). То же разделение, что у `apps/api`. Документ обновлён в этом же PR, чтобы не расходиться с кодом.

### Исправление, найденное живой проверкой

Первая живая проверка дала ровно тот сценарий, который план не предусмотрел: `CreateBranch` упал (404), но `StartTask` к этому моменту **уже** прошёл — в журнале остались `TaskStarted`, `ExecutionQueued`, `ExecutionStarted`, задача осталась в `in-progress` с живым Execution и без ветки, в которую можно коммитить. Повторных попыток нет (курсор сдвигается), то есть задача осталась бы в этом состоянии навсегда.

Порядок изменён на «ветка → `StartTask` → `Accept`»: самый вероятный отказ (неверный репозиторий, отсутствующий/недействительный токен, недоступность GitHub) теперь не трогает задачу, она остаётся в Ready — ровно тот путь восстановления, который эпик и обещает («задача остаётся в Ready и может быть запущена вручную через `apps/api`»). Цена — возможная осиротевшая ветка, что безвредно.

Проверено вживую до и после, на одном и том же отказе:

| | до исправления | после |
| --- | --- | --- |
| Состояние задачи | `in-progress` | `ready` |
| События в журнале | `TaskPlanned` + `TaskStarted` + `ExecutionQueued` + `ExecutionStarted` | только `TaskPlanned` |

Порядок закреплён тестом (`TestDispatch_BranchFailureLeavesTaskInReady`), чтобы не отрегрессировать молча.

### Open Questions

1. **Формат идентификатора репозитория рассогласован — реальные вызовы GitHub строят неверный URL.** `github.Provider` документирует и ожидает `owner/name`, подставляя значение прямо в `/repos/%s/...`. Но в проекте репозитории хранятся с хостом: тесты используют `github.com/org/repo`, и я подключал `github.com/nikibrdev/ai-studio-os`. В живой проверке это дало путь `/repos/github.com/nikibrdev/ai-studio-os/git/ref/heads/main` — заведомо некорректный для GitHub API независимо от валидности токена.

   Почему не поймали раньше: `TestGoldenPath_Infrastructure` использует in-memory фейк `RepositoryProvider` (по причине из Open Question TASK-050 — токена нет в каждой среде), поэтому построение URL настоящим адаптером с принятым в проекте форматом не проверялось ни разу.

   Отдельно: `platform.RepositoryProvider` прямо оговаривает «repository identifiers are strings until ADR-013 fixes the managed project connection format» — а ADR-013, принятая мной 2026-07-23 в этой сессии, формат так и не зафиксировала. То есть вопрос, на который ссылался контракт, остался открытым при закрытии ссылавшейся ADR.

   Требуется решение (нормализовать в адаптере, отбрасывая хост, либо сменить хранимый формат на `owner/name`) — это не входит в scope TASK-082 и затрагивает EPIC-005; предлагаю отдельный BUGFIX перед TASK-085, иначе сквозной прогон эпика не пройдёт.
2. **Полный путь до `Accept` вживую не подтверждён** — нужен действительный `GITHUB_TOKEN` (и, для содержательной работы агента, `ANTHROPIC_API_KEY` + собранный образ `ai-studio-os-execution`). Сборка `ExecutorTask` доказана юнит-тестом по всем полям; сквозной прогон — TASK-085.
