# TASK-099: Диспетчеризация QA при входе задачи в Testing

## Тип

feature

## Эпик

[EPIC-013 Роли PM и QA](../../docs/roadmap/EPIC-013-pm-qa-roles.md)

## Цель

Когда задача входит в Testing, Orchestrator запускает агента роли QA Engineer, получает отчёт проверки и записывает его как Artifact. Задача **остаётся в Testing** — приёмочное решение принимает только человек.

## Контекст

Задача входит в Testing по одобренному ревью: `ReviewCompleted` с целевым состоянием `testing` (целевое состояние несёт `Envelope.WithData` — механизм из EPIC-004). Это и есть событие для диспетчеризации QA.

**Контрольная точка сохраняется структурно:** агент не имеет доступа к `apps/api`, а Orchestrator вызывает только запись артефакта — не `CompleteTesting`. Ни один путь исполнения не сливает Pull Request и не переводит задачу в Done.

**Отчёт — Artifact, а не вердикт.** В отличие от ревью, где решение принимал агент (ADR-008 это разрешает), здесь решение остаётся человеку. Отчёт QA — свидетельство выполненной проверки, то есть именно артефакт; для записи уже есть `ResultService`.

## Scope

### Входит

- Бутстрап QA-исполнителя — тем же `EnsureExecutor`.
- Обработка входа задачи в Testing (`ReviewCompleted` с целевым `testing`): своя запись QA-исполнителя, ветка задачи (та же, что ревьюировали), `ExecutorTask` с ролью `qa`, `Accept`, слежение.
- При успехе — чтение отчёта и запись его как Artifact через `ResultService`; задача остаётся в Testing.
- **Ничего не выдумывается при отказе:** неудача, таймаут, отсутствующий или нераспознанный отчёт не создают артефакт-заглушку. Пустой отчёт, выглядящий как проверка, опаснее отсутствия отчёта: человек принял бы решение, полагая, что проверка была.
- `Finish` — всегда.
- Тесты: успешный путь (артефакт записан, задача **в Testing**, `CompleteTesting` не вызван, merge не произошёл); отказные пути; событие `ReviewCompleted` с целевым `in-progress` (правки запрошены) → QA **не** запускается.

### Не входит

- Автоматическое приёмочное решение и слияние — прямо запрещены ADR-007.
- Оценка качества отчёта — это и есть то, что читает человек в контрольной точке.
- Запуск проверок платформой вместо агента.

## Критерии приёмки

- [x] QA-исполнитель регистрируется и активируется идемпотентно — тем же `EnsureExecutor`.
- [x] При входе задачи в Testing запускается агент роли `qa`; отчёт записывается как опубликованный артефакт `TestReport`.
- [x] Задача **остаётся в Testing**; `CompleteTesting` не вызывается, Pull Request не сливается — закреплено тестом, **проверенным как падающий** при умышленном нарушении.
- [x] Запрос правок (`ReviewCompleted` → `in-progress`) QA не запускает — закреплено тестом, проверенным как падающий.
- [x] Отказ, таймаут или нераспознанный отчёт не создают артефакт-заглушку; `Finish` вызван.
- [x] `make verify` — чисто.

## Отчёт о выполнении

### Задача

TASK-099 — диспетчеризация QA при входе задачи в Testing.

### Что сделано

- **`qa.go`** — `ReportExecutor`, `enteredTesting`, `dispatchEnteredTesting`, `recordReport`. Механизм переиспользован из EPIC-010/011/013: выбор исполнителя по роли, слежение, гарантированный `Finish`.
- **Триггер читает целевое состояние явно.** `ReviewCompleted` неоднозначен по имени: одобрение и запрос правок — одно событие, различает их только прикреплённое целевое состояние. Запрос правок QA не запускает.
- **Отчёт — артефакт без Execution.** У прогона QA нет Execution, поэтому `RecordDraftArtifact` не годится (он требует Running Execution). Добавлен `ResultService.RecordTestReport`. Спецификация это прямо допускает: ссылка на породившее Execution **необязательна**, её отсутствие «не делает Artifact менее полноценным» (Behavioral Invariant 3), а тип `TestReport` спецификация называет вместе с почти мгновенным переходом Draft → Published — поэтому отчёт создаётся и публикуется одним шагом.
- **Автор отчёта — `claude-code`, а не «неизвестен»**, хотя спецификация допускает и второе для полностью автоматических прогонов: прогон автоматический, но атрибутируемый — человек, читающий отчёт, должен знать, что его писал агент.
- **`CompleteTesting` не вызывается ни на одном пути**; ничего не выдумывается при отказе.

### Найденное в собственных тестах — трижды вакуумное утверждение

Самое важное утверждение эпика («автоматика не проходит контрольную точку») **не работало**, и это выяснилось только потому, что я проверил его умышленным нарушением: вставил вызов `CompleteTesting` в рабочий код и ожидал падения теста. Тест прошёл. Три причины, каждую пришлось устранять отдельно:

1. **Фикстура была слабее продакшена:** `CompletionService` в `newDispatchFixture` собирался **без `Views`**, хотя `main.go` его передаёт. Без проекции `CompleteTesting` не мог найти ссылку на Pull Request и падал на `ErrPullRequestUnknown` — то есть «ничего не слилось» выполнялось по постороннему обстоятельству. Ровно та же болезнь, что нашлась в `testDeps()` при BUGFIX-009.
2. **Прогон разработчика в фикстуре не производил коммитов**, поэтому Pull Request не открывался и ссылки не существовало вовсе. Добавлен коммит-артефакт.
3. **Проекция фикстуры не знала о `ReviewRequested`** — события, прошедшие через сервисы, в неё не попадают. Добавлено воспроизведение опубликованных событий через `Observe`, как это делает `Poller.Seed` в продакшене.

Только после всех трёх исправлений умышленное нарушение стало падать. Побочный эффект: счётчики артефактов и `Finish` пришлось перевести на **дельты** — фикстура делит один фейковый бэкенд с прогоном разработчика, и абсолютные значения включали чужую работу.

### Рекомендации

- **Проверять «падает ли тест без фикса» нужно и для утверждений о том, что чего-то НЕ произошло.** Отрицательные утверждения выполняются сами собой, если система не в состоянии произвести запрещённое действие. Здесь три независимых обстоятельства делали нарушение невозможным — и все три были свойствами фикстуры, а не кода.
- **Фикстура обязана повторять сборку продакшена.** Второй случай за проект (после `testDeps()` в BUGFIX-009), когда сервис в тестах собран с меньшим числом зависимостей, чем в `main.go`. Стоит сверять состав зависимостей фикстуры с composition root при каждом добавлении поля в сервис.
- **Общий фейк между шагами сценария требует дельт, а не абсолютных счётчиков.** Абсолютные значения проходят, пока предыдущий шаг ничего не делал, и ломаются при первом же изменении фикстуры — что и произошло здесь дважды.
