# BUGFIX-010: read-модель не восстанавливается при старте процесса

## Тип

fix

## Эпик

Вне эпика — исправление; обнаружено живой проверкой TASK-095 (EPIC-012), затрагивает `apps/api` (EPIC-008).

## Цель

`apps/api` создаёт `TaskProjection` пустой и только подписывается на шину — он **никогда не восстанавливает её из журнала событий**. Любой перезапуск процесса стирает всю read-модель: `GET /decisions` возвращает пустой список, `GET /projects/{p}/tasks/{id}` отвечает 404 — хотя данные целы в PostgreSQL. Задача — восстанавливать проекцию при старте.

**Уточнение, найденное при реализации:** `apps/orchestrator` этим дефектом **не** затронут — его `Poller.Start` вычитывает журнал целиком и прогоняет через `Seed` (TASK-082), то есть проекцию он восстанавливает. Изначально задача была сформулирована шире («оба процесса»); проверка кода это опровергла, и формулировка исправлена, а не оставлена «на всякий случай».

## Контекст

Обнаружено живой проверкой TASK-095, при перезапуске `apps/api` ради GitHub-токена:

```text
=== projection after restart (данные в БД есть!) ===
{"decisions":[]}
```

В базе в этот момент лежали `TASK-001` в `ready` и `TASK-002` в `testing` — то есть задача, **ожидающая решения человека**, существовала, а список ожидающих был пуст.

**Почему это серьёзно именно для EPIC-012.** Весь смысл эпика — показать человеку, что ждёт его решения. После перезапуска API человек видит «Задач, ожидающих решения, нет.» и делает вывод, что от него ничего не требуется. Молчаливое «всё в порядке» вместо «я потерял состояние» — худший вид отказа для механизма контрольных точек.

**Средства для исправления существуют с EPIC-005 и не используются.** `eventbus.ReadJournal` написан ровно для этого («rebuilding read projections… from durable history rather than from the live in-process bus»), `TaskProjection.Rebuild` — тоже, а [BUGFIX-004](BUGFIX-004-projection-rebuild-loses-envelope-data.md) специально починил точность воспроизведения. Ни один процесс их не вызывает.

**Почему не заметили раньше.** Тесты создают проекцию и сразу наполняют её событиями в том же процессе — перезапуска в тестах не бывает. Живые проверки EPIC-010/011 тоже не перезапускали API посреди сценария. Дефект проявляется только там, где процесс переживает данные, то есть в реальной эксплуатации.

## Scope

### Входит

- `apps/api` — при старте восстановить проекцию из журнала **до** начала обслуживания запросов. Читается через уже существующий порт `application.EventJournal` (`Since(0)` — «всё»), а не импортом `eventbus`: порт для этого и есть.
- `apps/orchestrator` — только комментарий, поясняющий, что восстановление read-модели и позиция курсора опроса — **разные** вещи: история прогоняется целиком, а курсор стартует с вершины, иначе перезапуск заново задиспетчеризировал бы уже выполненную работу. Кода менять не требуется.
- Интеграционный тест на реальном PostgreSQL: события записаны, **новая** проекция восстановлена из журнала, состояние и описательные поля совпадают с ожидаемыми.

### Не входит

- Устойчивое хранение курсора опроса Orchestrator'а — отдельное ограничение EPIC-010, не связано с read-моделью.
- Инкрементальное обновление проекции из журнала во время работы (сейчас — подписка на шину внутри процесса, чего достаточно).
- Изменение `TaskProjection` и `ReadJournal`: оба уже умеют всё нужное.

## Отчёт о выполнении

### Задача

BUGFIX-010 — read-модель `apps/api` не восстанавливалась при старте.

### Что сделано

- **`apps/api` восстанавливает проекцию из журнала до обслуживания запросов.** Читается через уже существующий порт `application.EventJournal` (`Since(0)` — «вся история»), а не импортом `eventbus`: порт для этого и создавался, и это избавляет `main.go` от второго инфраструктурного импорта.
- **Отказ восстановления — фатален.** Стартовать с пустой read-моделью хуже, чем не стартовать: пустой список выглядит как ответ «ничего не ждёт», а не как отказ.
- **Уточнена формулировка задачи по факту кода.** Изначально задача утверждала, что дефект в обоих процессах. Проверка показала, что `apps/orchestrator` **уже** восстанавливает проекцию — его `Poller.Start` прогоняет журнал через `Seed` (TASK-082). Формулировка исправлена, а не оставлена «на всякий случай»: неверное описание области дефекта хуже, чем узкое.
- **Зафиксировано, что восстановление и курсор — разные вещи** (комментарий в `poller.go`, README обоих приложений): историю read-модель обязана знать целиком, а курсор опроса стартует с вершины — иначе перезапуск задиспетчеризировал бы уже выполненную работу повторно.

### Изменённые файлы

- `apps/api/main.go` — `rebuildViews`, вызов до запуска сервера.
- `apps/orchestrator/poller.go` — комментарий о раздельности восстановления и курсора.
- `internal/infrastructure/wiring/golden_path_integration_test.go` — интеграционный тест; `newActiveProjectWithID` (id теперь можно задать, чтобы прогоны не сталкивались в общей БД).
- `apps/api/README.md`, `apps/orchestrator/README.md`.

### Как проверялось

- **Дефект зафиксирован живой проверкой TASK-095 до исправления:** после перезапуска `apps/api` при непустой базе `GET /decisions` вернул `{"decisions":[]}` — то есть задача, ожидающая решения человека, существовала, а список ожидающих был пуст.
- **После исправления, тем же способом:** в логе старта `read model rebuilt from 453 journaled events`, `/decisions` отдаёт ожидающее решение.
- **Интеграционный тест проверен как падающий без исправления** — при удалении вызова `Rebuild` падает с «task is not in the rebuilt projection — a restart would hide it from the human». Тест имитирует перезапуск честно: **новая** проекция, ни на что не подписанная, наполняется только из журнала.
- **Проверена и описательная часть, не только состояние** — урок BUGFIX-004: после восстановления сверяются `Title`/`Scope`, а также что задача попадает в список ожидающих решения с верным типом решения.
- **Разобрано расхождение, замеченное при проверке:** в БД пять задач в состояниях контрольных точек, а в `/decisions` — одна. Причина законная: у четырёх **ноль событий в журнале** — они записаны напрямую интеграционными тестами PostgreSQL-хранилища, минуя Application Layer. Проекция строится только из событий (ADR-014), поэтому не знает о них. Дефекта нет; проверено запросом, а не предположением.
- `make verify` — чисто; весь набор `-tags integration` — зелёный.

### Open Questions

- **Восстановление читает весь журнал целиком.** На нынешнем масштабе (453 события) это мгновенно, но растёт линейно. Когда станет заметно, понадобится либо снимок проекции, либо чтение с известной позиции — отдельное решение, не нужное сейчас.

### Рекомендации

- **Дефект нашёлся не тестом, а перезапуском процесса.** Тесты создают проекцию и наполняют её в одном процессе — перезапуска в них не бывает по построению. Стоит включать «перезапустить процесс посреди сценария» в живые проверки: это дешёвый способ найти всё, что живёт только в памяти.
- **Средства для исправления существовали с EPIC-005 и просто не вызывались.** `ReadJournal` и `Rebuild` написаны ровно для этого, BUGFIX-004 отдельно починил точность replay — и всё это не использовалось ни одним процессом. Полезно спрашивать про готовые механизмы: «а кто это вызывает?».
- **Молчаливая пустота — худший вид отказа для механизма контрольных точек.** «Ничего не ждёт решения» неотличимо от «я потерял состояние». Там, где пустой ответ штатный, стоит отдельно проверять, что он получен по правильной причине.
