# TASK-093: Dashboard — раздел «Ждут решения»

## Тип

feature

## Эпик

[EPIC-012 Контрольные точки человека](../../docs/roadmap/EPIC-012-human-checkpoints.md)

## Цель

Показать человеку, какие задачи ждут его решения, — раздел в `apps/dashboard`, читающий операцию из TASK-092.

## Контекст

Сейчас `apps/dashboard` показывает список проектов → задачи проекта → детали задачи, и ничто не выделяет задачи, стоящие в контрольной точке. Человек, чтобы понять, что от него требуется, должен просматривать задачи вручную.

Задача — только чтение; действия подтверждения добавляет TASK-094. Разделение сознательное: у Dashboard нет ни одной мутирующей операции, поэтому первый мутирующий UI стоит вводить отдельным шагом, а не вперемешку с новым экраном.

## Scope

### Входит

- Раздел/страница «Ждут решения»: задачи, ожидающие решения человека, с указанием какого именно (приём DoR / приёмочное решение), с переходом к деталям задачи.
- Отражение того же признака в уже существующих местах, если это не требует переделки их структуры (например, отметка в списке задач проекта).
- Состояния загрузки и ошибки — по существующим соглашениям `apps/dashboard` (`loading.tsx`/`error.tsx`).
- Тесты (Vitest + React Testing Library, как в EPIC-009): отображение непустого списка, пустого списка, различение двух типов решения.

### Не входит

- Кнопки подтверждения и любые мутирующие запросы — TASK-094.
- Изменение API — операция уже есть (TASK-092).
- Аутентификация и разделение пользователей (ADR-012).

## Отчёт о выполнении

### Задача

TASK-093 — раздел «Ждут решения» в `apps/dashboard`.

### Что сделано

- **`/decisions`** — список задач, ожидающих решения, с типом решения, ссылкой на задачу и указанием проекта; ссылка в шапке.
- **Тип решения не выводится в UI из состояния** — берётся из поля `awaitingDecision`, которое отдаёт сервер (TASK-092). Соответствие «состояние → решение» это правило платформы, дублировать его в UI запрещено `module-boundaries.md`.
- **Названия решений заданы в одном месте** (`decisionLabels` в клиенте API), чтобы формулировка не расходилась между экранами — на следующем шаге те же названия понадобятся кнопкам подтверждения.
- **Пустой список — объясняющий текст**, а не пустой экран: отсутствие ожидающих решения нормальное состояние.
- **Учтено, что номера задач не уникальны между проектами:** список ключуется парой «проект/задача» и подписывает проект — иначе два `TASK-001` из разных проектов слились бы визуально и в React-ключах (ADR-011, BUGFIX-003).

### Найдено попутно: типы в тестах не проверялись вообще

Изменение `TaskView` (новое обязательное поле) сломало типы в **трёх** файлах тестов — и **все проверки остались зелёными**: `pnpm test` прошёл 12 тестов, `pnpm build` собрался успешно. Причина: Vitest снимает типы, не проверяя их, а `next build` проверяет только то, что импортирует приложение — тестовые файлы в этот граф не входят.

То есть любая ошибка типов в тестах `apps/dashboard` до сих пор проходила и локально, и в CI незамеченной.

Закрыто: добавлен скрипт `typecheck` (`tsc --noEmit`) и шаг в CI перед тестами. **Проверено, что шаг ловит именно этот дефект:** при повторном удалении поля `pnpm typecheck` падает с `error TS2741: Property 'awaitingDecision' is missing`, тогда как `pnpm test` в тот же момент сообщает «12 passed».

### Рекомендации

- **«Все проверки зелёные» и «код типизирован верно» — разные утверждения.** Здесь три файла с ошибками типов прошли через тесты и сборку. Стоит помнить, что `vitest` и `next build` не заменяют `tsc --noEmit`, и что новый шаг проверки полезно один раз проверить на реальном дефекте — иначе неизвестно, работает ли он.
- **Обязательное поле в общем типе — самый дешёвый способ найти все места использования.** Сделать `awaitingDecision` необязательным было бы удобнее в моменте, но тогда фикстуры молча остались бы неполными, а `typecheck` не показал бы, где именно данные неполны.
- Названия решений стоит держать в одном месте с самого начала: на следующем шаге те же строки нужны кнопкам, и расхождение формулировок между списком и кнопкой сбивало бы с толку именно в тот момент, когда человек принимает решение.
