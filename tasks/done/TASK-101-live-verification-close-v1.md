# TASK-101: Живая проверка всех четырёх ролей, закрытие EPIC-013 и v1.0

## Тип

test

## Эпик

[EPIC-013 Роли PM и QA](../../docs/roadmap/EPIC-013-pm-qa-roles.md)

## Цель

Подтвердить вживую: платформа проводит задачу через все четыре роли и **останавливается перед каждой контрольной точкой**, а человек проходит их из интерфейса. Закрыть EPIC-013 и вместе с ним v1.0 First Public MVP.

## Контекст

Уроки трёх предыдущих эпиков: сквозная живая проверка нашла восемь дефектов (BUGFIX-004…010), из них два — только перезапуском процесса и разбором перед кодом. Здесь новых швов сразу несколько: две новые роли, уточнение описательных полей после создания (снятое допущение проекции), чтение артефактов через API.

**Главное, что проверяется, — не «работает», а «останавливается».** Ценность v1.0 в том, что автоматика доводит задачу до контрольной точки и не идёт дальше. Прогон обязан подтвердить, что ни PM, ни QA не прошли свою точку, а не только что они что-то произвели.

## Scope

### Входит

- Сквозной прогон на реальной инфраструктуре: создание задачи → PM уточняет (задача **в Backlog**) → человек принимает DoR из UI → Developer работает → Reviewer выносит вердикт → QA готовит отчёт (задача **в Testing**) → человек принимает приёмочное решение из UI → Done со слиянием.
- **Проверка остановок:** после PM задача в Backlog, после QA — в Testing; в журнале нет `TaskPlanned` и `TestsPassed` до соответствующего действия человека.
- **Проверка, что агенты не могут пройти точки структурно:** сетевой allowlist песочницы не содержит `apps/api`; попытка обращения из песочницы к нему не проходит (проверить фактически, а не по конфигурации).
- Проверка отказных путей: агент любой роли упал — задача не сдвинулась, заглушек не создано.
- Перезапуск `apps/api` и `apps/orchestrator` посреди сценария (приём, найденный в TASK-095) — состояние сохраняется.
- Сверка **в БД через `psql`** и в GitHub через `gh api`.
- Полный набор `-tags integration` на живой инфраструктуре.
- Закрытие EPIC-013 и **v1.0**: критерии, ROADMAP, PROJECT_MANIFEST, PROJECT_HEALTH, CHANGELOG.

### Не входит

- Публикация релиза `v1.0.0` (тег, GitHub Release) — отдельное решение владельца проекта после закрытия эпика; релизный процесс описан в [git-workflow.md](../../docs/development/git-workflow.md).
- Оценка содержательного качества работы агентов.

## Отчёт о выполнении

### Задача

TASK-101 — живая проверка всех четырёх ролей, закрытие EPIC-013.

### Что подтверждено вживую

Реальный PostgreSQL, реальный Docker, настоящий приватный репозиторий, действительный GitHub-токен, два отдельных процесса:

| Шаг | Подтверждение |
| --- | --- |
| Бутстрап всех ролей | Четыре записи реестра созданы идемпотентно: developer, reviewer, project-manager, qa |
| PM на `TaskCreated` | Диспетчеризован, упал без ключа; «task stays as it is for a human» |
| **Контрольная точка 1** | **Задача в Backlog, `TaskPlanned` — ноль** |
| Приём DoR человеком | `204`, задача → Ready |
| Developer на `TaskPlanned` | Диспетчеризован, ветка `feature/TASK-001-v1-0` создана, Execution → Failed |
| Reviewer на `ReviewRequested` | Диспетчеризован; «task stays in review for a human»; `ReviewCompleted` — ноль |
| QA при входе в Testing | Диспетчеризован; «no report recorded, task stays in testing» |
| **Контрольная точка 2** | **Задача в Testing, `TestsPassed`/`MergeCompleted`/`TaskCompleted` — ноль** |
| Перезапуск `apps/api` | Read-модель восстановлена из 518 событий, задача по-прежнему `testing`/`acceptance` |
| Приёмочное решение человека | **Pull Request #2 слит в настоящем GitHub** (`merged=true`), задача → Done |
| Порядок событий | `TestsPassed` → `MergeCompleted` → `TaskCompleted` — точно по ADR-008 |
| Утечки | Ноль оставшихся контейнеров и сетей |

**Недостижимость `apps/api` из песочницы проверена фактически:** контейнер, запущенный во внутренней сети (той же, что у песочницы исполнения), получил `000` — маршрута нет. Проверка по конфигурации была бы слабее: allowlist можно прочитать и ошибиться в выводе.

### Что осталось непроверенным — честно

**Содержательная работа агентов вживую не проверена: `ANTHROPIC_API_KEY` в этой среде отсутствует.** Все четыре роли доходят до запуска `claude` в песочнице и падают с `exit code 1`.

Это ограничение оказалось **и полезным**: оно превратило прогон в проверку самого важного свойства v1.0 — что при отказе агента **ничего не происходит**. Ни одна из четырёх ролей не сдвинула задачу, не записала заглушку и не прошла контрольную точку. Такой отказной путь на настоящей инфраструктуре ценнее, чем успешный прогон на фейках.

Не проверено: качество предложений PM, вердиктов Reviewer, отчётов QA и кода Developer — то есть содержательная сторона, а не механика.

### Рекомендации

- **Отрицательная проверка — главный инструмент этого эпика.** «Задача в Backlog» можно получить и по случайности; «ноль событий `TaskPlanned` в журнале» — нельзя. Там, где ценность в том, что система чего-то **не** делает, проверять нужно отсутствие следа, а не наличие состояния.
- **Отсутствие ключа провайдера стоит рассматривать как режим проверки, а не только как ограничение.** Оно дало сквозную проверку всех отказных путей на реальной инфраструктуре — то, что специально воспроизвести было бы трудоёмко.
- **Проверять свойства безопасности фактически.** Недостижимость API из песочницы читалась из кода как очевидная; запуск контейнера в той же сети занял минуту и превратил вывод в факт.
