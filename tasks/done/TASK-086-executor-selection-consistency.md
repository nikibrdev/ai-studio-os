# TASK-086: Согласовать выбранного исполнителя с фактически запускаемым бэкендом

## Тип

fix

## Эпик

[EPIC-011 Роли исполнителей](../../docs/roadmap/EPIC-011-executor-roles.md)

## Цель

Устранить расхождение, найденное живой проверкой EPIC-010 (Open Question 2): Orchestrator выбирает запись исполнителя из реестра, но запускает бэкенд независимо от неё — в событиях фиксируется один исполнитель, работает другой. Это предпосылка появления второй роли (Reviewer): с двумя записями расхождение станет наблюдаемым.

## Контекст

Живая проверка TASK-085 показала: при нескольких Active-исполнителях с ролью Developer выбирается первый по id — им оказалась запись `exec-store-1`, оставшаяся от интеграционных тестов, — тогда как фактически запускался собственный бэкенд через `NewExecutor`. На чистой установке запись одна, поэтому дефект не проявляется; [EPIC-010](../../docs/roadmap/EPIC-010-orchestrator.md) прямо указывает решить его до появления второго исполнителя.

Две отдельные проблемы в одном месте:

1. **Выбор зависит от посторонних записей.** «Первый Active с нужной ролью» — не выбор, а совпадение порядка по id. Бутстрап создаёт запись с известным идентификатором, но диспетчеризация его не предпочитает.
2. **Запись и бэкенд не связаны.** `NewExecutor` — фабрика без параметров: она создаёт `agents/claude-code` независимо от того, какая запись реестра была выбрана. Для одной роли и одного бэкенда это незаметно, для нескольких — источник неверных событий.

## Scope

### Входит

- Диспетчеризация предпочитает **собственную запись бутстрапа** для роли (детерминированно, по известному идентификатору), а не первую подходящую по порядку.
- Фабрика бэкенда связывается с выбранной записью: сигнатура `NewExecutor` получает роль/идентификатор исполнителя, чтобы созданный бэкенд соответствовал тому, что записано в событиях.
- Тесты: выбор не меняется от присутствия посторонних Active-записей с той же ролью; выбранный идентификатор совпадает с тем, что попадает в события; отсутствие собственной записи роли — понятная ошибка, а не молчаливый выбор чужой.

### Не входит

- Правило выбора среди **нескольких** собственных исполнителей одной роли (масштабирование) — за пределами v1.0, требует признака занятости, который отсутствует в доменной модели.
- Признак занятости исполнителя в спецификации Executor — отдельное доменное решение (см. риски EPIC-010).

## План реализации

**Ключевая идея:** сделать соответствие записи и бэкенда **структурным**, а не поддерживаемым по договорённости. Идентификатор записи выводится из роли, а фабрика бэкенда получает роль — тогда «выбрана одна, работает другая» становится невыразимым, а не просто исправленным.

1. `bootstrap.go` — идентификатор записи выводится из роли: `executorIDForRole(role) = "executor-claude-code-" + role`. Для Developer это даёт ровно тот же `executor-claude-code-developer`, что и раньше, поэтому существующие установки не требуют миграции. `EnsureDeveloperExecutor` обобщается в `EnsureExecutor(ctx, svc, store, role)` — Reviewer (TASK-088) добавится вызовом, а не копией.
2. `dispatch.go` — вместо «первый Active с нужной ролью» искать **свою запись по точному идентификатору**:
   - запись найдена и Active с нужной ролью → выбрана;
   - найдена, но не Active или без роли → понятная ошибка (а не молчаливый переход к чужой записи);
   - не найдена → понятная ошибка с указанием ожидаемого идентификатора.

   Так посторонние записи в реестре перестают влиять на выбор по построению: их идентификаторы просто не совпадают.
3. `NewExecutor` получает роль: `func(role shared.Role) (platform.Executor, error)`. Идентификатор записи выводится из той же роли, поэтому запись и бэкенд согласованы структурно. `ErrNoDeveloperExecutor` обобщается в `ErrNoExecutorForRole`.
4. `main.go` — фабрика передаёт роль дальше (для `agents/claude-code` конструктор один на все роли, ADR-007; различать роли будет промпт — TASK-087).
5. Тесты:
   - **воспроизведение сценария живой проверки**: в реестре посторонняя Active-запись с ролью Developer и меньшим id (как `exec-store-1`) — выбирается всё равно своя;
   - идентификатор в опубликованных событиях совпадает с ролью, для которой создан бэкенд;
   - своя запись не Active → ошибка, `Accept` не вызван, задача остаётся в Ready;
   - своей записи нет → ошибка с ожидаемым идентификатором.
6. `apps/orchestrator/README.md` — правило выбора и почему оно именно такое.
7. `make verify`.

## Отчёт о выполнении

### Задача

TASK-086 — согласовать выбранную запись исполнителя с фактически запускаемым бэкендом (Open Question 2 EPIC-010).

### Что сделано

**Соответствие сделано структурным, а не поддерживаемым по договорённости** — это главное решение задачи. Идентификатор записи выводится из роли (`executorIDForRole`), и фабрика бэкенда получает **ту же** роль. Поэтому «выбрана одна запись, работает другая» стало невыразимым, а не просто исправленным: чтобы они разошлись, нужно передать в два места разные роли.

- `bootstrap.go` — `EnsureDeveloperExecutor` обобщён в `EnsureExecutor(ctx, svc, store, role)`; идентификатор выводится из роли. Для Developer это даёт ровно прежний `executor-claude-code-developer`, поэтому **существующие установки не требуют миграции** — проверено сравнением строк, а не предположением. Reviewer (TASK-088) добавится вызовом, а не копией функции.
- `dispatch.go` — вместо сканирования «первый Active с нужной ролью» поиск **своей** записи по точному идентификатору. Посторонние записи теперь не могут повлиять на выбор в принципе: их идентификаторы не совпадают.
- **Присутствующая, но непригодная запись — ошибка, а не переход к другой.** Переход и был тем механизмом, которым две сущности могли снова разойтись; `ErrNoDeveloperExecutor` разделён на `ErrNoExecutorForRole` (записи нет) и `ErrExecutorNotUsable` (есть, но не Active или без роли). Текст ошибки называет ожидаемый идентификатор, чтобы оператор понял, что делать.
- `NewExecutor` получил параметр роли; `main.go` передаёт её (для `agents/claude-code` конструктор один на все роли — ADR-007, различать роли будет промпт в TASK-087).

### Как проверялось

- **Регрессионный тест воспроизводит сценарий живой проверки буквально:** в реестре посторонняя Active-запись `exec-store-1` (тот самый идентификатор из TASK-085, и он сортируется **раньше** собственного, то есть id-сканирование дошло бы до него первым) плюс своя запись. Проверяется, что `Execution.ExecutorID()` — собственный идентификатор.
- **Тест подтверждён как ловящий дефект.** При возврате прежней семантики (`if !e.AvailableForAssignment() || !e.HasRole(role)` вместо сравнения идентификатора — компилирующаяся замена, воспроизводящая старое поведение точно) тест падает с `execution executor = "exec-store-1", want ... "executor-claude-code-developer"`. С исправлением — проходит. Первая попытка проверки дала ошибку сборки и потому ничего не доказывала; повторил корректно.
- Ещё два теста: своя запись не Active → `ErrExecutorNotUsable`, задача остаётся в Ready, `Accept` не вызван; своей записи нет при наличии посторонней с другой ролью → `ErrNoExecutorForRole`, и текст ошибки содержит ожидаемый идентификатор.
- `make verify` — чисто; все тесты пакета зелёные.

### Рекомендации

- **Предпочитать структурную согласованность проверкам.** Дефект существовал потому, что связь записи и бэкенда поддерживалась намерением автора, а не типами: фабрика без параметров физически не могла знать, что выбрали. Вывод обоих из одного значения устраняет класс ошибки, а не экземпляр. Тот же приём стоит применить, если появится третья связанная сущность (например, промпт под роль — TASK-087).
- **Наивный «первый подходящий» — часто не выбор, а совпадение порядка.** Здесь он работал только потому, что запись была одна; сломался ровно тогда, когда появилась вторая. Стоит перечитать похожие места (первый репозиторий проекта в `repositoryOf` — то же свойство, но там ограничение осознано и задокументировано).
