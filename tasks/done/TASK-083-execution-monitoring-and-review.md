# TASK-083: Слежение за исполнением, Pull Request, RequestReview

## Тип

feature

## Эпик

[EPIC-010 Orchestrator](../../docs/roadmap/EPIC-010-orchestrator.md)

## Цель

Довести автоматизацию Developer-шага golden path до конца: после `Accept` (TASK-082) следить за исполнением до терминального состояния, зафиксировать произведённые артефакты, открыть Pull Request и перевести задачу в Review — либо, при неудаче, корректно завершить Execution как Failed.

## Контекст

`ResultService`/`CompletionService` (EPIC-004) уже реализуют нужные use-case'ы (`RecordDraftArtifact`, `PublishArtifact`, `SucceedExecution`, `FailExecution`, `RequestReview`) — эта задача только вызывает их в правильном порядке из `apps/orchestrator`, ничего не меняя в Application Layer. Открытие Pull Request'а — обязанность вызывающего кода (`agents/claude-code/README.md`), не адаптера: `Executor.Artifacts()` возвращает только `Commit`.

## Scope

### Входит

- Опрос `Executor.Status(ctx)` после `Accept` до терминального состояния (`succeeded`/`failed`), с таймаутом (константа, например 30 минут — предохранитель от зависшего контейнера).
- При успехе: `Executor.Artifacts(ctx)` → `ResultService.RecordDraftArtifact` для каждого коммита → `PublishArtifact` → `RepositoryProvider.OpenPullRequest` (заголовок/описание — из полей задачи) → `ResultService.SucceedExecution` → `CompletionService.RequestReview`.
- При неудаче/таймауте: `ResultService.FailExecution`.
- `Executor.Finish(ctx)` — вызывается всегда (успех, неудача, таймаут, паника обработчика — `defer`), чтобы контейнер не оставался запущенным.
- Юнит-тесты на фейковом `platform.Executor`/`RepositoryProvider`: успешный путь целиком, путь с ошибкой исполнения, таймаут.

### Не входит

- Ретраи при сбое — сознательно не входит в эпик (см. «Не входит» EPIC-010).
- Диспетчеризация Reviewer/QA после `ReviewRequested` — следующий эпик декомпозиции v1.0.

## Критерии приёмки

- [x] Успешное исполнение приводит задачу в состояние Review с опубликованным Artifact и открытым Pull Request'ом.

## План реализации

### Решение: слежение синхронное, внутри обработчика события

Альтернатива — горутина на каждое исполнение, чтобы цикл опроса не простаивал. Отвергнута для этой версии:

- **Доменная модель не отслеживает занятость исполнителя.** `Executor.AvailableForAssignment()` — это `state == Active`, и ничего больше; два `TaskPlanned` подряд назначили бы работу одному и тому же исполнителю параллельно. Синхронное слежение это предотвращает естественным образом — работа выстраивается в очередь, что соответствует уже принятому ограничению «один исполнитель на роль». Ввести признак занятости — доменное решение (изменение спецификации Executor), а не то, что стоит изобретать в Orchestrator.
- Горутины потребовали бы аккуратного завершения (ожидание незакрытых песочниц при остановке процесса), то есть заметной сложности в первой версии.

**Цена, принимаемая осознанно:** пока исполнение идёт, цикл опроса не обрабатывает другие события — включая события других проектов. Для доверенной однопользовательской установки (тот же принцип, что ADR-012) это приемлемо; фиксируется в README как ограничение, не замалчивается.

### Поведение при отказе на каждом шаге

Проработано заранее — урок TASK-082, где неверный порядок шагов обнаружился только вживую.

| Шаг | Отказ | Что делаем | Состояние после |
| --- | --- | --- | --- |
| Опрос `Status` | Транзиентная ошибка | Логируем, повторяем до таймаута | Execution Running |
| Опрос `Status` | Таймаут (контейнер зависший) | `FailExecution` | Execution Failed, Task In Progress |
| `Artifacts` | Ошибка чтения `git log` | `FailExecution` | Execution Failed, Task In Progress |
| `RecordDraftArtifact`/`PublishArtifact` | Ошибка домена/хранилища | `FailExecution` | Execution Failed, часть артефактов записана |
| `OpenPullRequest` | GitHub недоступен | `FailExecution` | Execution Failed, артефакты записаны, PR нет |
| `SucceedExecution` | Ошибка домена | Логируем, `Finish` | Execution как есть |
| `RequestReview` | Ошибка перехода | Логируем, `Finish` | Execution Succeeded, Task In Progress |
| Любой | — | `Finish` **всегда**, через `defer` | Песочница уничтожена |

**Важно и проверяется тестом:** `ExecutionFailed` **не переводит Task** — ни в state machine, ни в проекции (`targetState` его не разбирает). Задача остаётся In Progress с проваленным Execution; вернуть её в работу — решение человека через `apps/api`. Это существующий доменный дизайн, а не пробел этой задачи; фиксируется в README, чтобы не выглядело потерянным переходом.

### Шаги

1. `apps/orchestrator/monitor.go` — `monitorExecution(ctx, backend platform.Executor, run *execution.Execution, projectID, taskID, repo, branch string, view application.TaskView) error`:
   - `defer` вызов `Finish` с логированием его собственной ошибки (не маскируя основную).
   - Цикл опроса `Status` с интервалом `statusPollInterval` (константа, 10с) и общим таймаутом `executionTimeout` (константа, 30 мин) — предохранитель от зависшей песочницы.
   - При `"succeeded"`: `Artifacts` → на каждый `RecordDraftArtifact` (поля `Type`/`Origin`/`Author` адаптера ложатся в доменные как есть: `"Commit"`/`"produced"`/`"claude-code"`, `Origin` совпадает с `artifact.OriginProduced`; ID — хеш коммита, он же в `platform.Artifact.ID`) + `PublishArtifact` → `OpenPullRequest` (заголовок/тело из полей задачи) → `SucceedExecution` → `RequestReview`.
   - При `"failed"`/таймауте/любой ошибке до `SucceedExecution`: `FailExecution`.
   - Артефакты записываются **до** `SucceedExecution`: `RecordDraftArtifact` требует Execution в состоянии Running (доменный инвариант), после `Succeed` он уже не Running.
2. `dispatch.go` — `Dispatcher` получает `Results *application.ResultService`, `Completion *application.CompletionService`; `dispatchTaskPlanned` после `Accept` вызывает `monitorExecution`.
3. `main.go` — собрать и передать оба сервиса.
4. Тесты (`monitor_test.go`, на фейках, с малыми интервалами через поля вместо констант — иначе тест ждал бы минуты): успешный путь целиком (артефакты записаны и опубликованы, PR открыт, Execution Succeeded, Task в Review, `Finish` вызван); `"failed"` от исполнителя (Execution Failed, PR не открыт, `Finish` вызван); таймаут; ошибка `Artifacts`; ошибка `OpenPullRequest`; `Finish` вызывается во всех путях; отсутствие артефактов (успех без коммитов — PR открывать нечему, но это не ошибка исполнения).
5. `README.md` — раздел о слежении, таблица отказов, ограничение про блокировку цикла, замечание про Task при ExecutionFailed.
6. `make verify`; живая проверка — до реального запуска песочницы дойти не удастся без токена и образа (TASK-085), поэтому здесь проверяется, что при отказе на реальном шаге состояния меняются как заявлено.

## Отчёт о выполнении

### Задача

TASK-083 — слежение за исполнением до конца: артефакты, Pull Request, завершение Execution, запрос ревью.

### Что сделано

- **`monitor.go`** — `monitorExecution`: опрос `Status` до терминального состояния, затем запись исхода. `Finish` — через `defer`, то есть вызывается на **любом** пути выхода, включая ошибки и таймаут; его собственная ошибка логируется, а не возвращается, чтобы не маскировать исход самой работы.
- **Матрица отказов проработана до кода**, а не обнаружена вживую — прямой урок TASK-082. Все семь строк таблицы (в плане и README) закреплены тестами.
- **Порядок внутри успешного пути обусловлен доменом:** артефакты записываются **до** `SucceedExecution`, потому что прикрепить артефакт можно только к Execution в состоянии Running (Execution Behavioral Invariant 4) — после `Succeed` он уже не Running и `RecordDraftArtifact` был бы отвергнут.
- **Слежение синхронное** — решение зафиксировано в плане и README с обоснованием: доменная модель не отслеживает занятость исполнителя (`AvailableForAssignment` — это только «Active ли он»), поэтому два `TaskPlanned` подряд назначили бы работу одному бэкенду параллельно. Синхронность выстраивает работу в очередь. Цена (цикл не обрабатывает другие события во время исполнения) названа в README как ограничение, а не замолчана. Признак занятости — доменное решение, не изобретаемое в Orchestrator.
- **Транзиентная ошибка `Status` не прекращает ожидание** — логируется и повторяется до таймаута: один сбой `docker` не повод бросать живое исполнение. Неизвестное состояние от адаптера трактуется как «ещё работает» по той же причине.
- **Провал агента — это исход, а не ошибка Orchestrator'а:** `Handle` возвращает `nil`, Execution переходит в Failed. Ошибкой считаются только сбои наших шагов (артефакты, PR, переходы).
- **Успех без коммитов** обрабатывается отдельно: открывать PR нечему, но Execution всё равно успешен и задача уходит в Review — человек увидит, что ничего не произведено.
- **Косметические сбои не роняют работу:** неудачный `RequestReview` у провайдера (комментарий к PR) логируется — PR уже открыт, и это главное.
- Значения `Type`/`Origin`/`Author` адаптера ложатся в доменные без перекодирования (`"Commit"`/`"produced"`/`"claude-code"`; `"produced"` совпадает с `artifact.OriginProduced`); идентификатор артефакта — хеш коммита, что делает его прослеживаемым до реальной истории.
- `StatusPollInterval`/`ExecutionTimeout` — поля с fallback на константы: тесты ставят миллисекунды вместо минут, продакшен использует 10с/30мин.

### Рекомендации

- **Матрица отказов до кода сработала:** в TASK-082 неверный порядок шагов нашёлся только живым прогоном; здесь все семь отказных путей были продуманы заранее и сразу закреплены тестами — правок по ходу не потребовалось. Стоит применять тот же приём к любому шагу, который трогает внешние системы.
- **Синхронность — самое заметное ограничение этой версии.** Если появится потребность вести несколько задач одновременно, первым шагом должно быть доменное решение о занятости исполнителя (спецификация Executor), а не горутины в Orchestrator: иначе одному бэкенду будет назначено две работы сразу.
- Задача при `ExecutionFailed` остаётся In Progress — это существующий доменный дизайн. Если практика покажет, что человеку неудобно возвращать такие задачи вручную, это отдельное решение о переходе в state machine, а не правка Orchestrator'а.
