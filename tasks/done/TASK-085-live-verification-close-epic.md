## Контекст

Тот же принцип, что TASK-056 (EPIC-006)/TASK-070 (EPIC-008): unit-тесты на фейках не заменяют проверку на настоящей инфраструктуре. Честно принятое ограничение — как и в EPIC-006, реальный `ANTHROPIC_API_KEY` может отсутствовать в среде проверки; в этом случае проверяется механика (переходы состояний, запуск/остановка контейнера, создание ветки, вызов `Accept`/`Finish`), а не качество ответа AI-провайдера — ограничение документируется явно, не замалчивается.

## План реализации

**Решение владельца проекта (2026-07-25):** сквозная проверка выполняется против **одноразового репозитория**, а не против `ai-studio-os` — чтобы автоматически созданные ветка и Pull Request не оставляли следа в основном репозитории. Создан `nikibrdev/ai-studio-os-e2e-sandbox` (private, с начальным коммитом на `main`); удаляется одной командой после проверки.

**Что доступно и чего нет:**

| Условие | Состояние |
| --- | --- |
| PostgreSQL | есть (`docker compose`) |
| Образ `ai-studio-os-execution` | есть (собран в EPIC-006/TASK-053) |
| Действительный `GITHUB_TOKEN` | есть (через уже выполненную аутентификацию `gh`, scope `repo`) |
| `ANTHROPIC_API_KEY` | **нет** — агент запустится, но реального вызова провайдера не будет |

Отсутствие ключа провайдера — то же принятое ограничение, что зафиксировано в EPIC-006 (Open Question TASK-056). Оно означает, что агент не напишет код, поэтому **содержательная** часть (реальные коммиты → Pull Request с кодом) непроверяема. Проверяемо всё остальное, включая то, что раньше было недостижимо: реальное создание ветки в GitHub, реальный запуск и уничтожение контейнера, реальное поведение `Artifacts`/`Status`.

### Шаги

1. Поднять `apps/api`, создать проект, подключить репозиторий-песочницу, активировать, создать и запланировать задачу — всё через реальные HTTP-вызовы, без прямых обращений к БД.
2. Запустить `apps/orchestrator` с действительным токеном и собранным образом.
3. Наблюдать и зафиксировать: подхват `TaskPlanned` из журнала → выбор исполнителя → **реальное создание ветки** → `StartTask` → **реальный запуск контейнера** → `Status` → `Artifacts` → исход → `Finish`.
4. Проверить в GitHub: ветка создана; Pull Request — открыт или нет, и почему.
5. Проверить в БД: состояния задачи и Execution, последовательность событий в журнале.
6. **Отдельно проверить подозрение, найденное при подготовке:** `Artifacts` выполняет `git log --format=%H%n%s -n 20` без ограничения диапазона, то есть возвращает историю ветки целиком, а не только коммиты, сделанные исполнением. На репозитории с существующей историей это означало бы, что чужие коммиты записываются как «произведённые» артефакты. Подтвердить или опровергнуть **фактом**, а не чтением кода.
7. По результатам: закрыть критерии эпика честно (что подтверждено, что осталось ограничением), обновить ROADMAP/PROJECT_MANIFEST/PROJECT_HEALTH/CHANGELOG, при необходимости открыть BUGFIX на найденное.
8. Удалить репозиторий-песочницу.

## Отчёт о выполнении

### Задача

TASK-085 — сквозная живая проверка Orchestrator на реальной инфраструктуре, закрытие EPIC-010.

### Что сделано

Проверка выполнена **трижды**: первый прогон нашёл дефект, второй подтвердил его исправление и оставил второй дефект, третий (после обоих исправлений) — финальный.

**Найдено и исправлено два блокирующих дефекта, оба существовали с EPIC-006 и были невидимы для 200+ тестов:**

1. **[BUGFIX-006](BUGFIX-006-container-clone-url-doubled-host.md)** — скрипт клонирования строил `https://github.com/github.com/owner/name.git`: **ни одно** реальное исполнение не могло начаться, все падали с `exit 128` без указания причины. Тот же класс дефекта, что BUGFIX-005, во втором месте потребления того же значения.
2. **[BUGFIX-007](BUGFIX-007-artifacts-reports-inherited-history.md)** — `Artifacts` возвращал унаследованную историю ветки как произведённые исполнением коммиты: на репозитории с историей чужой коммит был бы записан как артефакт с `Origin: produced` и по нему открылся бы Pull Request.

Без первого эпик не мог выполнить своё заявленное назначение; без второго первый же успешный прогон записал бы неверные данные. Оба исправлены, оба подтверждены живой проверкой до/после, оба закрыты регрессионными тестами, каждый из которых проверен как **падающий** без исправления.

### Что подтверждено вживую

Реальный PostgreSQL, реальный Docker, реальный приватный репозиторий (`nikibrdev/ai-studio-os-e2e-sandbox`), действительный GitHub-токен, собранный образ `ai-studio-os-execution`, два отдельных процесса (`apps/api` и `apps/orchestrator`), всё через настоящие HTTP-вызовы:

| Что | Подтверждение |
| --- | --- |
| Межпроцессный подхват события | `TaskPlanned`, опубликованный `apps/api`, прочитан Orchestrator'ом из журнала по курсору — то, что невозможно через `Bus.Subscribe` |
| Наполнение проекции из журнала | Заголовок/scope/критерии доехали до `ExecutorTask` (иначе агент получил бы пустой промпт) |
| Выбор исполнителя | Active Developer найден через `ExecutorStore.List` |
| **Реальное создание ветки в GitHub** | Три ветки `feature/TASK-001-*` созданы в репозитории-песочнице |
| Переход задачи через Application Layer | `TaskStarted` → `ExecutionQueued` → `ExecutionStarted` в журнале |
| **Реальный запуск песочницы** | Контейнер и сеть созданы, клон выполнен (после BUGFIX-006) |
| Опрос `Status` до терминального состояния | Исполнение доведено до `failed` |
| `FailExecution` при неудаче | Execution в состоянии `failed`, задача остаётся In Progress — ровно как задокументировано |
| **Отсутствие ложных артефактов** | 0 артефактов и 0 Pull Request'ов — после BUGFIX-007 унаследованная история не записывается |
| `Finish` во всех путях | Ноль оставшихся контейнеров и сетей после каждого из трёх прогонов |
| Идемпотентность бутстрапа | Повторный запуск не добавил ни записи в реестр, ни событий |

### Что осталось непроверенным — честно

**Содержательная работа агента не проверена: `ANTHROPIC_API_KEY` в этой среде отсутствует.** Исполнение доходит до запуска `claude` в песочнице и падает с `exit code 1` (в первом прогоне было 128 — отказ клонирования; после BUGFIX-006 отказ сдвинулся к самому агенту). Это то же ограничение, что зафиксировано в EPIC-006 (Open Question TASK-056), и оно означает, что **не проверены**: реальные коммиты агента, открытие Pull Request'а по ним, `SucceedExecution` и переход задачи в Review.

Эта часть покрыта юнит-тестами по всем путям (9 тестов слежения, включая полный успешный путь с проверкой содержимого PR), но **тестами, а не живым прогоном**. Критерий эпика отмечен частично (`[~]`), а не как выполненный.

### Рекомендации

- **Сквозная живая проверка нашла четыре дефекта за один эпик** (BUGFIX-004/005 при разработке, BUGFIX-006/007 при этой проверке), все — в швах между слоями, все невидимые для юнит-тестов. Практический вывод: такая задача должна быть в **каждом** эпике, который интегрируется с внешней системой, и выполняться **до** того, как эпик объявляется готовым, а не после.
- **Общая причина всех четырёх дефектов одна:** каждая сторона шва тестировалась своими данными. Проекция — настоящими `Envelope`, адаптеры — краткой формой репозитория, песочница — фейком, игнорирующим команду. Правило: фейк должен подавать **то же значение и в той же форме**, что реальный вызывающий код, а если код выбирает между вариантами вызова — фейк обязан их различать.
- **Наивный выбор исполнителя.** Прогон вскрыл, что Orchestrator выбрал `exec-store-1` (запись, оставшуюся от интеграционных тестов), а не собственный `executor-claude-code-developer`, и при этом фактически запустил **свой** бэкенд через `NewExecutor`. То есть в событиях зафиксирован один исполнитель, а работал другой. На чистой установке записи одна, поэтому это не проявляется, но выбор «первый Active с ролью» слишком наивен: он не предпочитает собственную запись и допускает расхождение записанного с фактическим. Не исправлялось здесь (за пределами scope, требует решения о правиле выбора) — вынесено в Open Questions эпика.
