# BUGFIX-006: клон в песочнице строил URL с удвоенным хостом — любое исполнение падало с exit 128

## Тип

fix

## Эпик

Вне эпика — исправление; обнаружено сквозной живой проверкой TASK-085 (EPIC-010), затрагивает уже закрытый EPIC-006 (`agents/claude-code/container`).

## Цель

Ни одно реальное исполнение не могло начаться: скрипт клонирования в песочнице подставлял идентификатор репозитория в URL, уже содержащий хост, из-за чего получалось `https://github.com/github.com/owner/name.git` — `git clone` падал с `fatal: repository not found` (exit 128), а платформа сообщала лишь «exit code 128», ничего не говоря о причине. Задача — привести идентификатор к виду, который ожидает URL клонирования, и сделать так, чтобы такой отказ был диагностируем.

## Контекст

Обнаружено **первой сквозной живой проверкой** (TASK-085) против настоящего репозитория: Orchestrator корректно создал ветку в GitHub, перевёл задачу, запустил контейнер — и исполнение сразу завершилось с `exit code 128`.

**Причина.** `agents/claude-code/container/script.go` строит URL так:

```go
shellQuote("https://x-access-token@github.com/" + repository + ".git")
```

`repository` приходит из `platform.ExecutorTask.Repository`, то есть в каноническом хранимом виде `<host>/<owner>/<name>` ([platform.RepositoryProvider](../../internal/platform/repository.go), зафиксировано в BUGFIX-005). Хост в шаблоне и хост в значении складываются.

**Подтверждено фактом** до исправления — воспроизведён ровно тот URL, который строит контейнер:

```text
Cloning into '/tmp/repo'...
remote: Not Found
fatal: repository 'https://github.com/github.com/nikibrdev/ai-studio-os-e2e-sandbox.git/' not found
```

И контрольная проверка с тем же токеном и той же веткой, но со снятым хостом:

```text
CLONE OK
```

То есть удвоение хоста — единственная причина; ни токен, ни ветка, ни приватность репозитория ни при чём.

**Это тот же класс дефекта, что BUGFIX-005, в другом месте.** Там неверный путь строил GitHub REST-адаптер, здесь — скрипт клонирования в песочнице. Урок, записанный в отчёте BUGFIX-005 («тест должен подавать в адаптер то же значение, которое реально хранит платформа»), не был применён ко второму месту, где то же значение используется. Тесты `container` подают в `StartParams.Repository` короткое `org/repo`, поэтому удвоения не видели; живой прогон EPIC-006 (TASK-056) шёл против репозитория, указанного вручную в краткой форме.

## Scope

### Входит

- `agents/claude-code/container/script.go` — приведение идентификатора к `owner/name` перед подстановкой в URL клонирования (снятие схемы и хоста, суффикса `.git`), с проверкой результата.
- Ошибка вместо молчаливого построения неверного URL: `Start` возвращает понятную ошибку, если идентификатор неразбираем, — чтобы отказ не выглядел как `exit 128` из недр git.
- Тесты: таблица нормализации; тест, что в собранном скрипте URL содержит `github.com` **ровно один раз** для хранимого формата с хостом (то есть тест, которого не хватало); тест на отказ при неверном идентификаторе.
- `agents/claude-code/README.md` — зафиксировать ожидаемый формат и нормализацию.

### Не входит

- Изменение канонического хранимого формата — он зафиксирован BUGFIX-005 и остаётся `<host>/<owner>/<name>`.
- `Artifacts` возвращает историю ветки целиком, а не только произведённые коммиты — отдельный дефект, найденный тем же прогоном (BUGFIX-007).
- Поддержка хостингов кроме GitHub — адаптер по построению GitHub-специфичен.

## Отчёт о выполнении

### Задача

BUGFIX-006 — скрипт клонирования в песочнице строил URL с удвоенным хостом.

### Что сделано

- **`normalizeRepository`** в `agents/claude-code/container/script.go` — снимает схему, хост (регистронезависимо) и суффикс `.git`, затем **проверяет**, что осталось ровно два непустых сегмента; иначе `ErrInvalidRepository` с исходным значением в сообщении.
- **`cloneAndRunScript` теперь возвращает ошибку**, а `Start` строит скрипт **до создания сети и прокси** — неразбираемый идентификатор не должен оставлять за собой Docker-ресурсы, которые потом надо убирать.
- **Дублирование с `internal/infrastructure/github` осознанно:** `agents/` не может импортировать `internal/` (`module-boundaries.md`), а выносить в `pkg/` общий хелпер ради двух вызовов — значит заводить публичный контракт раньше реальной необходимости. Причина продублирована в комментарии, чтобы следующий читатель не счёл это копипастой.
- `agents/claude-code/README.md` — формат идентификатора, нормализация и объяснение, почему дефект был невидим.

### Как проверялось

- **Дефект доказан фактом до исправления** — воспроизведён ровно тот URL, который строил контейнер, внутри того же образа исполнения:

  ```text

  ```

  И **контрольная проверка** с тем же токеном, той же веткой и тем же образом, но со снятым хостом: `CLONE OK`. То есть причина — именно удвоение, а не токен, ветка или приватность репозитория.
- **Регрессионный тест подтверждён как ловящий дефект:** при временном возврате пред-исправленного поведения падает с «clone URL mentions github.com 2 times, want exactly 1»; с исправлением проходит.
- **Живой сквозной прогон после исправления** (реальный приватный репозиторий, реальный токен, реальный образ, полный путь через `apps/api` → журнал → Orchestrator): код возврата исполнения сменился **с 128 на 1**. 128 — `fatal` от git (клон не удался); 1 — падение уже самой команды агента из-за пустого `ANTHROPIC_API_KEY`, то есть отказ сдвинулся за пределы клонирования. Ветка `feature/TASK-001-after-clone-fix` создана в GitHub, контейнер запущен и уничтожен (`Finish` — ноль оставшихся контейнеров и сетей).

### Рекомендации

- **Тот же урок, третий раз, и я его не применил.** В отчёте BUGFIX-005 записано: «тест должен подавать в адаптер то же значение, которое реально хранит платформа». Ровно то же значение используется во втором месте — в URL клонирования — и там проверки не появилось. Практический вывод: при исправлении дефекта формата данных **надо сразу найти все места, где это значение потребляется**, а не только то, где отказ наблюдался. Для идентификатора репозитория таких мест было два: GitHub REST API и URL клонирования.
- Оба дефекта формата (BUGFIX-005/006) были невидимы для тестов и стали видны только сквозным прогоном против настоящего репозитория. Это подтверждает ценность TASK-085 как отдельной задачи эпика: два блокирующих дефекта на один прогон.
