# BUGFIX-005: формат идентификатора репозитория — GitHub-адаптер строил неверный URL

## Тип

fix

## Эпик

Вне эпика — исправление; обнаружено живой проверкой TASK-082 (EPIC-010), затрагивает уже закрытый EPIC-005 (GitHub-адаптер).

## Цель

Любая реальная операция с GitHub падала с невнятным `404 Not Found`, потому что адаптер подставлял в путь API идентификатор репозитория в том виде, в каком его хранит платформа (`github.com/owner/name`), тогда как GitHub REST API ожидает в `/repos/{...}` только `owner/name`. Задача — принять формат, зафиксировать его в контракте и сделать так, чтобы принятый в проекте вид идентификатора работал, а заведомо неверный давал понятную ошибку вместо запроса к несуществующему пути.

## Контекст

Обнаружено живой проверкой TASK-082: Orchestrator дошёл до `CreateBranch` и получил

```text
github: GET /repos/github.com/nikibrdev/ai-studio-os/git/ref/heads/main:
unexpected status 404: {"message": "Not Found", ...}
```

Путь `/repos/github.com/nikibrdev/...` некорректен для GitHub API независимо от валидности токена: после `/repos/` должно идти ровно `owner/name`.

**Рассогласование форматов.** `github.Provider` документирует «repo is always "owner/name"» и подставляет значение прямо в `fmt.Sprintf("/repos/%s/...", repo)`. Но платформа хранит идентификаторы с хостом: так их создаёт `ProjectService.ConnectRepository` в реальном использовании, так они записаны в тестах (`github.com/org/repo`, `github.com/nikibrdev/ai-studio-os` в `TestGoldenPath_Infrastructure`).

**Почему не поймали раньше.** Тесты самого адаптера используют только `"org/repo"` — они самосогласованы, но ни один не проверяет формат, который платформа реально хранит. А `TestGoldenPath_Infrastructure` и все тесты Application Layer используют in-memory фейк `RepositoryProvider` (по причине из Open Question TASK-050: токена GitHub нет в каждой среде), поэтому построение URL настоящим адаптером с настоящим форматом не проверялось ни разу. Дефект существовал с EPIC-005 и был невидим до первого реального вызова.

**Незакрытый вопрос контракта.** `platform.RepositoryProvider` прямо оговаривает: «repository identifiers are strings until ADR-013 fixes the managed project connection format». [ADR-013](../../docs/adr/ADR-013-managed-projects.md), принятая 2026-07-23 при открытии v1.0, формат **не зафиксировала** — ADR закрыта, а вопрос, на который ссылался контракт, остался открытым. Тот же комментарий контракта до сих пор называет [ADR-008](../../docs/adr/ADR-008-git-policies.md) «Decision Required», хотя она принята.

**Решение архитектора (закрывает пробел ADR-013):** канонический хранимый вид — тот, что уже хранится (`<host>/<owner>/<name>`, например `github.com/nikibrdev/ai-studio-os`), а приведение к виду конкретного хостинга — обязанность адаптера. Обоснование: домен хранит то, что подключил человек, и остаётся провайдер-агностичным — хост в значении говорит, *какой* это хостинг, что понадобится при появлении второго провайдера; знание «для GitHub API нужно `owner/name`» принадлежит GitHub-адаптеру, а не домену. Вариант «сменить хранимый формат на `owner/name`» отвергнут: он потребовал бы миграции уже записанных данных и лишил бы идентификатор указания на хостинг, ничего не дав взамен.

## Scope

### Входит

- `internal/infrastructure/github/provider.go` — нормализация идентификатора перед подстановкой в путь: снятие схемы (`https://`, `http://`), префикса хоста (`github.com/`), суффикса `.git`; **валидация** результата (ровно два непустых сегмента) с понятной ошибкой вместо запроса к неверному пути. Применяется во всех шести операциях контракта.
- Новая sentinel-ошибка для неразбираемого идентификатора.
- Тесты: таблица нормализации (принятый в проекте вид с хостом, вид со схемой, `.git`, уже краткий вид, заведомо неверные значения); проверка, что реальные пути запросов формируются как `/repos/owner/name/...` именно для хранимого формата с хостом (то есть тест, которого не хватало).
- `internal/platform/repository.go` — зафиксировать формат в контракте; убрать две устаревшие ссылки (ADR-013 «зафиксирует формат» — зафиксирован здесь; ADR-008 «Decision Required» — принята).
- `internal/infrastructure/README.md` — раздел GitHub-адаптера: формат и нормализация.

### Не входит

- Смена хранимого формата и миграция данных — отвергнуто (см. «Решение»).
- Поддержка других хостингов (GitLab и т.п.) — адаптера нет, изобретать правила для него сейчас не нужно.
- Живые мутирующие вызовы GitHub (создание ветки/PR в настоящем репозитории) — это внешний побочный эффект в репозитории пользователя; корректность пути проверяется тестами против локального HTTP-сервера-заглушки, как и все существующие тесты адаптера.

## План реализации

1. `provider.go` — `normalizeRepo(repo string) (string, error)`: снять схему, префикс `github.com/`, суффикс `.git`, обрезать `/`; проверить, что осталось ровно два непустых сегмента; иначе — `ErrInvalidRepository` с исходным значением в сообщении.
2. Применить во всех шести методах контракта; путь строить только из нормализованного значения.
3. `provider_test.go` — таблица нормализации; тест, что для `github.com/org/repo` сервер-заглушка получает `/repos/org/repo/...` (проверка через уже применяемый `httptest`); тест, что неверный идентификатор не доходит до HTTP.
4. `internal/platform/repository.go` — описать формат в контракте, убрать устаревшие оговорки про ADR-008/013.
5. `internal/infrastructure/README.md` — абзац про формат и нормализацию.
6. `make verify`; полный набор `-tags integration` на живом PostgreSQL.

## Отчёт о выполнении

### Задача

BUGFIX-005 — GitHub-адаптер строил неверный путь API из принятого в проекте формата идентификатора репозитория.

### Что сделано

- **Формат зафиксирован в контракте** (`internal/platform/repository.go`): канонический хранимый вид — `<host>/<owner>/<name>`, приведение к виду конкретного хостинга — обязанность адаптера. Это закрывает вопрос, который контракт адресовал ADR-013, а та не закрыла.
- **`normalizeRepo`** в GitHub-адаптере: снимает схему (`https://`/`http://`), хост (`github.com/`, `www.github.com/`, регистронезависимо), суффикс `.git`, обрезает `/` — и **проверяет**, что осталось ровно два непустых сегмента. Валидация здесь не менее важна, чем нормализация: неразбираемый идентификатор теперь даёт `ErrInvalidRepository` **до** HTTP-запроса, вместо запроса к бессмысленному пути и `404`, который выглядел как отсутствующий репозиторий или недействительный токен.
- Применено во **всех шести** операциях контракта, а не только в `CreateBranch`, где дефект проявился: остальные пять строят путь точно так же и сломались бы при первом же реальном вызове.
- **ADR-013 дополнена**: честно зафиксировано, что при её принятии (2026-07-23, в этой же сессии) был пропущен незакрытый вопрос, ответом на который она была назначена — `platform.RepositoryProvider` ссылался на неё как на место, где формат будет определён. Запись не переписана как «всё было верно»: дополнение прямо называет пропуск и указывает, где вопрос закрыт.
- **Устаревшая ссылка попутно исправлена**: тот же комментарий контракта называл ADR-008 «Decision Required», хотя она принята. Правка в одну строку в уже затронутом блоке — не расширение scope.
- `internal/infrastructure/README.md` — формат, нормализация, и почему дефект был невидим.

### Как проверялось

- **Регрессионный тест подтверждён как ловящий дефект:** при временном возврате пред-исправленного поведения `TestCreateBranch_AcceptsStoredHostPrefixedForm` падает; с исправлением проходит. Без этой проверки тест мог бы просто «всегда проходить».
- **Живая проверка до/после** на одном и том же сценарии (реальные HTTP-запросы к `apps/api`, задача, запланированная через API, Orchestrator дошёл до вызова GitHub):

  | | путь запроса |
  | --- | --- |
  | до | `GET /repos/github.com/nikibrdev/ai-studio-os/git/ref/heads/main` |
  | после | `GET /repos/nikibrdev/ai-studio-os/git/ref/heads/main` |

  Запрос по-прежнему не проходит (токен-заглушка недействителен), но путь теперь корректен — именно это и было дефектом.
- **Все существующие тесты адаптера прошли без единой правки** — подтверждает обратную совместимость с кратким видом `owner/name`.

### Рекомендации

- **Урок, общий с BUGFIX-004:** оба дефекта жили в шве между слоями и были невидимы, потому что каждая сторона тестировалась своими данными — адаптер краткой формой, а всё выше него фейком.
