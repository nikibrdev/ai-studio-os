# TASK-081: Каркас apps/orchestrator, бутстрап Developer-исполнителя, цикл опроса

## Тип

feature

## Эпик

[EPIC-010 Orchestrator](../../docs/roadmap/EPIC-010-orchestrator.md)

## Цель

Создать `apps/orchestrator` как отдельный запускаемый процесс: сборка зависимостей через `wiring.System` (по образцу `apps/api/main.go`), идемпотентная регистрация одного Developer-исполнителя при старте, цикл опроса `EventJournal.Since` с курсором в памяти. Без диспетчеризации событий — она в TASK-082/083; эта задача проверяется тем, что процесс стартует, видит собственный курсор и не падает при отсутствии новых событий.

## Контекст

`apps/orchestrator` сейчас — пустой каталог с `.gitkeep` (зарезервирован ещё в EPIC-002). Конфигурация (образ контейнера, GitHub-токен, ключ AI-провайдера, репозиторий проекта) — переменные окружения, тот же принцип, что `apps/api/main.go` (DSN, порт).

## Scope

### Входит

- `apps/orchestrator/main.go` — сборка `wiring.System` (DSN из `DATABASE_URL`, опционально `QDRANT_URL` — как `apps/api`), чтение конфигурации Orchestrator'а из переменных окружения (образ контейнера, `GIT_TOKEN`, AI-провайдер-ключ, репозиторий по умолчанию), запуск цикла опроса.
- Бутстрап: при старте — `ExecutorStore.List`, если Active Developer-исполнителя нет — `ExecutorService.Register` + `Activate` с фиксированным ID/backend (`agents/claude-code`, роль `developer`); идемпотентно — повторный запуск не создаёт дубликат.
- Цикл опроса: курсор в памяти (инициализация — момент запуска), периодический вызов `EventJournal.Since(ctx, cursor)` (интервал — константа, например 5с), обновление курсора по последнему полученному событию; для этой задачи — только логирование полученных событий (обработка `TaskPlanned` — TASK-082).
- Грациозное завершение по сигналу (`SIGINT`/`SIGTERM`), по образцу `apps/api/main.go`, если там уже есть такой обработчик — иначе добавить в обоих местах согласованно не требуется (только `apps/orchestrator` в scope этой задачи).
- `apps/orchestrator/README.md` — пока минимальный (назначение, переменные окружения, запуск); полное описание механизма — TASK-084.

### Не входит

- Обработка `TaskPlanned` (выбор исполнителя, `StartTask`, `Accept`) — TASK-082.
- Слежение за исполнением — TASK-083.
- Docker-образ/деплой Orchestrator'а — не входит в эпик (см. stack.md/toolchain — за пределами этой задачи).

## План реализации

1. `apps/orchestrator/config.go` — `Config` + `FromEnv()`: `DATABASE_URL` (через `postgres.DatabaseURLEnv`), `QDRANT_URL`, `EXECUTION_IMAGE` (по умолчанию `ai-studio-os-execution` — имя из `agents/claude-code/README.md`), `GITHUB_TOKEN` (через `github.TokenEnv`), `ANTHROPIC_API_KEY`, `POLL_INTERVAL` (по умолчанию 5с). Пустой `ANTHROPIC_API_KEY` — валиден (`claudecode.New` это допускает явно: механику песочницы можно проверять без реального вызова провайдера).
2. `apps/orchestrator/bootstrap.go` — `EnsureDeveloperExecutor(ctx, svc, store)`: идемпотентно приводит реестр к состоянию «есть один Active Developer-исполнитель» с фиксированным ID (`developerExecutorID`, константа) — `List` → если нет, `Register`; если есть и не Active и не Retired, `Activate`; если уже Active — ничего. Фиксированный ID и есть механизм идемпотентности (а не поиск по эвристике).
3. `apps/orchestrator/poller.go` — `Poller{Journal, Interval, Handle, Log}`:
   - `Start(ctx)` — инициализирует курсор текущей вершиной журнала, чтобы не переигрывать всю историю при запуске (переигрывание заново задиспетчеризировало бы уже обработанные `TaskPlanned`). Вершина берётся через `Since(ctx, 0)` — порт другого способа не даёт; журнал на этом масштабе мал, неэффективность зафиксировать в отчёте.
   - `poll(ctx)` — один проход: `Since(cursor)` → на каждую запись вызвать `Handle`, сдвинуть курсор. Отдельный метод (не только `Run`) — чтобы тесты проверяли логику без таймеров.
   - `Run(ctx)` — цикл по `time.Ticker` до `ctx.Done()`.
   - **Ошибка `Handle` логируется, но курсор всё равно сдвигается** — иначе одно «отравленное» событие заблокирует цикл навсегда. Решение зафиксировать в комментарии и отчёте.
   - Ошибка самого `Since` — логируется, курсор не двигается, следующий тик повторит (транзиентная недоступность БД не должна ронять процесс).
4. `apps/orchestrator/main.go` — `main`/`run` по образцу `apps/api/main.go`: `wiring.New`, `EnsureDeveloperExecutor`, `Poller` с обработчиком-логгером (диспетчеризация — TASK-082), грациозное завершение по `SIGINT`/`SIGTERM` через `signal.NotifyContext`.
5. Тесты (`apps/orchestrator`, на фейках — без Docker и без БД):
   - `config_test.go` — значения по умолчанию, переопределение из окружения, разбор `POLL_INTERVAL`.
   - `bootstrap_test.go` — три пути идемпотентности (нет исполнителя / есть неактивный / уже Active) на `inmemory`-фейках `ExecutorStore`/`EventBus`; повторный вызов не создаёт дубликата и не публикует лишних событий.
   - `poller_test.go` — фейк `application.EventJournal`: курсор инициализируется вершиной; `poll` вызывает `Handle` на каждую запись и сдвигает курсор; ошибка `Handle` не останавливает обработку и не заставляет перечитывать запись; ошибка `Since` оставляет курсор на месте.
6. `apps/orchestrator/README.md` — минимальный (назначение, переменные окружения, запуск, ограничения); полное описание механизма — TASK-084.
7. `make verify`; живая проверка: `go run ./apps/orchestrator` против реального PostgreSQL — старт, бутстрап, идемпотентность при повторном запуске (проверить `psql`, что исполнитель один), реакция цикла на реальное событие, завершение по сигналу.

## Отчёт о выполнении

### Задача

TASK-081 — каркас `apps/orchestrator`, идемпотентный бутстрап Developer-исполнителя, цикл опроса журнала.

### Что сделано

- **`config.go`** — `Config`/`FromEnv`: `DATABASE_URL`, `QDRANT_URL`, `EXECUTION_IMAGE` (по умолчанию `ai-studio-os-execution`), `GITHUB_TOKEN`, `ANTHROPIC_API_KEY`, `POLL_INTERVAL` (по умолчанию 5с). Имена переменных БД и GitHub переиспользованы из их собственных пакетов (`postgres.DatabaseURLEnv`, `github.TokenEnv`), а не заведены параллельно. Отсутствие `DATABASE_URL` не проверяется здесь — `wiring.New` уже сообщает об этом точнее (`postgres.ErrDatabaseURLNotSet`); дублировать проверку значило бы получить два разных сообщения об одной ошибке. `POLL_INTERVAL` отвергается, если непарсится или неположителен (нулевой период — бесконечно частый опрос).
- **`bootstrap.go`** — `EnsureDeveloperExecutor`: фиксированный идентификатор `executor-claude-code-developer` **и есть** механизм идемпотентности (перезапуск находит ту же запись, а не добавляет новую). Четыре пути: нет записи → Register+Activate; не Active → Activate; уже Active → ничего; **Retired → ошибка**. Последнее — осознанно: Retired терминален в домене, и тихая регистрация замены под новым идентификатором оставила бы две записи и переопределила бы решение оператора вывести бэкенд из эксплуатации. Поиск идёт по идентификатору, а не по роли/бэкенду, чтобы чужие исполнители (`codex` и т.п.) не были приняты за свой.
- **`poller.go`** — `Poller{Journal, Interval, Handle, Log}`:
  - `Start` ставит курсор на вершину журнала, чтобы перезапуск не переигрывал историю (переигрывание задиспетчеризировало бы уже отработанные `TaskPlanned`).
  - `poll` — отдельный от `Run` метод, поэтому вся логика курсора проверяется без таймеров.
  - **Ошибка `Handle` логируется, курсор всё равно сдвигается** — иначе одно необрабатываемое событие заблокировало бы все последующие навсегда. Задача остаётся в текущем состоянии и может быть проведена вручную через `apps/api` — это строго лучше, чем заклинивший цикл.
  - **Ошибка `Since` оставляет курсор на месте** — следующий тик повторит то же окно: транзиентная недоступность БД не должна ни ронять процесс, ни пропускать события.
- **`main.go`** — по образцу `apps/api/main.go`; `signal.NotifyContext` вместо ручного `select` по каналу сигналов (здесь нет HTTP-сервера, который нужно гасить отдельно). Обработчик на этой задаче — только логирование; диспетчеризация — TASK-082, `Handler` для этого и вынесен в тип.
- **`README.md`** — назначение, границы по `module-boundaries.md`, переменные окружения, запуск, «почему опрос, а не подписка», и все четыре ограничения версии явным списком.
- **19 юнит-тестов** на фейках (без Docker и без БД): конфигурация (5), идемпотентность бутстрапа (5), курсор и цикл (9).

### Как проверялось

- `make verify` — чисто (fmt, golangci-lint `0 issues.`, vet, тесты, markdownlint `0 issues`, docs-check 1341 ссылка).
- Покрытие: логика — `FromEnv` 100%, `Start` 100%, `poll` 100%, `Run` 90%, `EnsureDeveloperExecutor` 73.3%; `main`/`run`/`logHandler` — 0%, это точка сборки, проверяемая живым запуском, а не юнит-тестом (у `apps/api/main.go` тестов нет вовсе — тот же принцип).
- **Живой запуск против реального PostgreSQL** (`go run ./apps/orchestrator`): процесс поднялся, забутстрапил исполнителя, поставил курсор на вершину (`seq 102`), начал опрос. В БД проверено (`psql`): запись `executor-claude-code-developer` — `backend=claude-code`, `roles={developer}`, `state=active`; в журнале ровно два события (`ExecutorRegistered`, `ExecutorActivated`) с `actor=orchestrator`.
- **Идемпотентность вживую:** второй запуск не добавил ни записи в реестр (`count=1`), ни событий в журнал (`count=2`) — не только юнит-тест на фейке.
- **Межпроцессный сценарий — главный результат задачи:** одновременно запущены `apps/api` (порт 8099) и `apps/orchestrator`. Реальный `POST /projects` → HTTP 201 → через один интервал опроса Orchestrator напечатал `event ProjectCreated (...) project="proj-orch-1784993178"`. Это ровно то, что было **структурно невозможно** через `Bus.Subscribe` (доставка только внутри своего процесса) — подтверждено на двух настоящих процессах, а не на фейках.
- **Завершение по сигналу — проверено частично, честно:** логика выхода из цикла подтверждена тестом (`TestPollerRun_StopsOnContextCancel` — `Run` возвращает `nil` при отмене контекста). Доставку самого `SIGINT`/`SIGTERM` в этой среде подтвердить не удалось: Git-Bash на Windows не доставляет POSIX-сигналы нативному Windows-бинарю предсказуемо (`timeout -s INT` завис, `timeout` с `SIGTERM` дал код 143 без прохождения грациозного пути). Это ограничение среды проверки, а не кода: связка «сигнал → контекст» — один вызов стандартной библиотеки (`signal.NotifyContext`), тот же, что уже используется в `apps/api/main.go`. Отмечено в критериях как `[~]`, а не как выполненное.

### Open Questions

- **Грациозное завершение по сигналу не проверено вживую** из-за ненадёжной доставки POSIX-сигналов из Git-Bash в нативный Windows-бинарь. Проверяется одной командой в Linux-среде (в том числе в CI-контейнере или Dev Container): запустить процесс, послать `SIGTERM`, убедиться, что в логе есть `stopping at seq N` и код возврата 0. Предлагаю сделать это в рамках живой проверки TASK-085, где Orchestrator и так будет запускаться вместе с Docker.

### Рекомендации

- `Poller.Start` ищет вершину журнала через `Since(ctx, 0)`, то есть вычитывает журнал целиком один раз при запуске. На текущем масштабе (сотня событий) это незаметно, но при росте журнала это станет заметной паузой на старте. Правильное решение — метод `LatestSeq` в порту `EventJournal`; вводить его сейчас, до появления проблемы, значило бы расширять порт «на будущее» — отдельная задача по реальной потребности.
- Обработчик-логгер (`logHandler`) в `main.go` — временный по построению: TASK-082 заменит его диспетчером. Тип `Handler` введён именно для этой замены, чтобы TASK-082 не переписывал цикл.
