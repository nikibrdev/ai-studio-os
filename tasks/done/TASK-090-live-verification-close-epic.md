# TASK-090: Живая проверка ролей, закрытие EPIC-011

## Тип

test

## Эпик

[EPIC-011 Роли исполнителей](../../docs/roadmap/EPIC-011-executor-roles.md)

## Цель

Подтвердить вживую на реальной инфраструктуре: два исполнителя в реестре не мешают друг другу, на `ReviewRequested` запускается агент роли Reviewer с правильным промптом, вердикт применяется через Application Layer. Закрыть эпик.

## Контекст

Урок EPIC-010: сквозная живая проверка нашла четыре дефекта, невидимых для тестов, и два из них были в швах, где каждая сторона тестировалась своими данными. Здесь появляется новый шов — вторая роль и передача вердикта, — поэтому проверка обязательна до объявления эпика готовым.

**Что проверяемо без `ANTHROPIC_API_KEY`.** Довести задачу до состояния Review можно вручную через `apps/api` (`request-review` на задаче In Progress), не дожидаясь успешного исполнения Developer'а. Значит диспетчеризация Reviewer, выбор исполнителя, промпт и уничтожение песочницы проверяются вживую; недостижимо только содержательное — реальный вердикт агента, а с ним и переход в Testing.

## Scope

### Входит

- Проверка предпосылки TASK-086 **на том же сценарии, что вскрыл дефект**: в реестре несколько Active-записей (включая постороннюю от интеграционных тестов) — выбор остаётся верным, и идентификатор в событиях совпадает с фактически запущенным бэкендом.
- Прогон: проект → задача → план → (исполнение Developer) → перевод в Review через `apps/api` → наблюдение за диспетчеризацией Reviewer.
- Сверка состояний **в БД и в GitHub напрямую**, а не по логам приложения (как в TASK-085).
- Проверка, что при неудаче агента задача остаётся в Review и вердикт не выдуман.
- Отсутствие утечек: ноль оставшихся контейнеров и сетей.
- Обновление критериев эпика (с честной частичной отметкой, если применимо), ROADMAP, PROJECT_MANIFEST, PROJECT_HEALTH, CHANGELOG.

### Не входит

- Открытие следующего эпика (механизм подтверждения человеком) — отдельная задача после закрытия.

## Отчёт о выполнении

### Задача

TASK-090 — живая проверка ролей на реальной инфраструктуре, закрытие EPIC-011.

### Что подтверждено вживую

Реальный PostgreSQL, реальный Docker, реальный приватный репозиторий (`nikibrdev/ai-studio-os-e2e-sandbox`), действительный GitHub-токен, собранный образ, два отдельных процесса, всё через настоящие HTTP-вызовы:

| Что | Подтверждение |
| --- | --- |
| **Выбор исполнителя не зависит от посторонних записей** | В реестр добавлены `aaa-stray-developer`/`aaa-stray-reviewer` — они сортируются **раньше** собственных записей, то есть под прежней логикой «первый Active с ролью» победили бы. Orchestrator выбрал `executor-claude-code-developer` и `executor-claude-code-reviewer` |
| Бутстрап двух ролей | Обе записи созданы и активированы при старте; повторный запуск дубликатов не добавил |
| Диспетчеризация Developer | Ветка `feature/TASK-001-roles-verification` создана в GitHub, песочница запущена, клон выполнен |
| **Диспетчеризация Reviewer** | На `ReviewRequested` запущен агент роли Reviewer со **своей** записью и **существующей** веткой (новая не создавалась) |
| **Вердикт не выдуман** | Агент упал (нет ключа) → задача осталась в `review`, `ReviewCompleted` в журнале **не появился**; в логе — «task stays in review for a human» |
| **Ревью не создаёт Execution** | В журнале ровно один `ExecutionQueued` — от Developer-этапа; документированное ограничение подтверждено вживую, а не только тестом |
| `Finish` во всех путях | Ноль оставшихся контейнеров и сетей после прогона |
| Отсутствие ложных артефактов и PR | 0 артефактов, 0 Pull Request'ов (агент коммитов не производил) |

Последовательность событий в журнале: `ProjectCreated` → `RepositoryConnected` → `ProjectActivated` → `TaskCreated` → `TaskPlanned` → `TaskStarted` → `ExecutionQueued` → `ExecutionStarted` → `ExecutionFailed` → `ReviewRequested`. Ни `ReviewCompleted`, ни второго `ExecutionQueued` — ровно как задокументировано.

### Что осталось непроверенным — честно

**Применение вердикта вживую не пройдено: `ANTHROPIC_API_KEY` в этой среде отсутствует.** Агент роли Reviewer запускается, но падает, не дойдя до решения. Значит **не проверены**: соблюдает ли агент конвенцию файла вердикта, и оба содержательных исхода (Testing при одобрении, In Progress при запросе правок). Они покрыты юнит-тестами, но тестами, а не живым прогоном.

Проверено при этом главное для безопасности: когда вердикта нет, платформа его **не выдумывает**. Критерий эпика отмечен частично (`[~]`), а не как выполненный.

### Найдено попутно

Полный прогон `-tags integration` вскрыл [BUGFIX-008](../done/BUGFIX-008-qdrant-upsert-not-waited.md): интеграционный тест Memory проходил **из-за собственного ретрая**, маскируя, что запись в Qdrant не была сразу доступна поиску (не передавался `wait=true`). К ролям отношения не имеет — найдено потому, что весь набор прогонялся на живой инфраструктуре. Исправлено и смержено до закрытия эпика.

### Рекомендации

- **Воспроизводить вживую именно тот сценарий, который вскрыл дефект.** Проверка выбора исполнителя ценна не тем, что «выбор работает», а тем, что посторонние записи были подобраны сортирующимися **раньше** собственных — то есть воссоздавали исходный отказ. Проверка «на чистой установке» ничего бы не доказала.
- **Полный набор интеграционных тестов на живой инфраструктуре стоит прогонять при закрытии каждого эпика**, даже если эпик к этим тестам отношения не имеет: BUGFIX-008 не имел ничего общего с ролями и нашёлся именно так.
- **Формулировка «тест проходит» — не то же самое, что «поведение верное».** BUGFIX-008 — второй случай в проекте (после записи о TASK-056 в README адаптера), когда зелёный результат скрывал неверное поведение: там читалась чужая история, здесь тест сам себя спасал ретраем. Стоит спрашивать не «прошёл ли», а «прошёл ли по той причине, по которой должен был».
