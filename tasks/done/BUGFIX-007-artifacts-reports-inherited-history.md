# BUGFIX-007: Artifacts возвращал историю ветки целиком, а не произведённые исполнением коммиты

## Тип

fix

## Эпик

Вне эпика — исправление; обнаружено сквозной живой проверкой TASK-085 (EPIC-010), затрагивает уже закрытый EPIC-006 (`agents/claude-code`).

## Цель

`Executor.Artifacts` обещает возвращать «коммиты, произведённые Claude Code на ветке задачи», но выполняет `git log` без ограничения диапазона, то есть отдаёт последние 20 коммитов ветки — включая всю историю, унаследованную от `main`. На любом репозитории с историей это означает, что чужие коммиты записываются платформой как **произведённые** артефакты (`Origin: produced`) и по ним открывается Pull Request. Задача — возвращать только то, что действительно появилось за время исполнения.

## Контекст

Обнаружено сквозной живой проверкой TASK-085. Команда в адаптере:

```go
[]string{"git", "log", "--format=%H%n%s", "-n", "20"}
```

Диапазона нет — это история `HEAD`, а ветка задачи создаётся из `main` и содержит всю её историю.

**Подтверждено фактом** на свежесозданной ветке репозитория-песочницы (внутри образа исполнения, после успешного клона):

```text
=== what Artifacts would report: git log --format=%H%n%s -n 20 ===
f347a0adcfec80a76c4978df29aa3575367c3b12
Initial commit
```

`Initial commit` — коммит README, созданный при инициализации репозитория; агент его не делал. Если бы исполнение дошло до успешного исхода, `ResultService.RecordDraftArtifact` записал бы его как артефакт с `Origin: produced`, `Author: claude-code`, а Orchestrator открыл бы по нему Pull Request. Оба факта — ложь о том, что произошло.

**Почему не поймали раньше.** Тесты адаптера подают фейковой песочнице заранее заданный вывод `git log` (в котором, естественно, только «произведённые» коммиты), поэтому проверяют разбор, а не выбор коммитов. Живой прогон EPIC-006 (TASK-056) шёл против репозитория с историей, и `Artifacts` тогда «успешно читал историю коммитов» — что было записано в README как успех, хотя это и есть проявление дефекта: читалась именно чужая история.

**Почему это не заблокировало EPIC-010 так же, как BUGFIX-006.** Дефект проявляется только на успешном исполнении, а успешное исполнение сейчас недостижимо без `ANTHROPIC_API_KEY`. Но оставлять его в компоненте, который объявляется готовым в v1.0, нельзя: он сработает в первый же реальный прогон с ключом и запишет неверные данные.

## Scope

### Входит

- `agents/claude-code/container/script.go` — после успешного клона (и до запуска команды) записывать SHA базового коммита в файл; экспортировать путь к нему, чтобы адаптер мог его прочитать.
- `agents/claude-code/executor.go` — `Artifacts` читает базовый SHA и запрашивает `git log <base>..HEAD`, то есть только коммиты, появившиеся после клона. Пустой диапазон (агент ничего не закоммитил) — корректный пустой результат, а не ошибка.
- Верхний предел числа коммитов сохраняется как **предохранитель** от неограниченного вывода, а не как способ ограничить выборку (диапазон уже её ограничивает).
- Тесты: `Artifacts` запрашивает диапазон от базового SHA; пустой диапазон даёт пустой результат; отсутствие файла с базовым SHA обрабатывается явно.
- `agents/claude-code/README.md` — уточнить описание `Artifacts` и снять формулировку, называвшую чтение чужой истории успехом.

### Не входит

- Изменение контракта `platform.Executor` — `Artifacts` остаётся четвёртой возможностью ADR-005 с той же сигнатурой.
- Определение базы через имя ветки (`origin/main`) — база берётся как фактический `HEAD` на момент клона, без предположений о том, как называется базовая ветка.

## План реализации

1. `container/script.go` — экспортировать `BaseSHAFile`; в скрипте после `cd <workspace>` добавить `git rev-parse HEAD > <BaseSHAFile>` внутрь цепочки `&&`, чтобы при неудачном клоне файл не создавался.
2. `executor.go` — `Artifacts`: прочитать базовый SHA (`cat`), затем `git log --format=%H%n%s <base>..HEAD` с предохранительным `-n`. Пустой вывод → `nil, nil`.
3. Тесты (`executor_test.go`, `proxy_test.go`/`script_test.go`): фейковая песочница отдаёт базовый SHA и вывод `git log`; проверить, что запрашивается именно диапазон; пустой диапазон; ошибка при недоступном базовом SHA.
4. `README.md` — описание `Artifacts`; исправить абзац про живой прогон TASK-056.
5. `make verify`; **живая проверка** внутри образа исполнения: на свежей ветке без новых коммитов — пусто; после тестового коммита — только он.

## Отчёт о выполнении

### Задача

BUGFIX-007 — `Artifacts` возвращал унаследованную историю ветки как произведённые исполнением коммиты.

### Что сделано

- **`container.BaseSHAFile`** — при клонировании фиксируется `HEAD` рабочей копии (`git rev-parse HEAD` внутри цепочки `&&`, то есть только при успешном клоне). Это граница между унаследованной историей и тем, что произведёт исполнение.
- **`Artifacts` запрашивает `git log <base>..HEAD`** вместо всей истории. База — фактический `HEAD` на момент клона, а не `origin/main`: так не приходится предполагать, как называется базовая ветка (Orchestrator использует `main`, но адаптер об этом знать не должен).
- **Различены три исхода**, которые раньше сливались: пустой диапазон — корректный пустой результат (агент ничего не закоммитил); отсутствующий или пустой базовый SHA — ошибка (клон не завершился); непустой диапазон — произведённые коммиты.
- **Предел `-n` сохранён как предохранитель** от неограниченного вывода, но перестал быть способом ограничить выборку: её ограничивает диапазон. Значение поднято с 20 до 100 и переименовано в `maxReportedCommits` с комментарием о назначении — 20 в роли «предохранителя» выглядело подозрительно похожим на попытку ограничить именно выборку.
- **Фейковая песочница в тестах стала учитывать команду.** Прежняя игнорировала аргументы и возвращала один и тот же вывод на любой вызов — именно поэтому дефект был невидим: тест проверял разбор вывода, но не то, какую команду адаптер вообще issues. Теперь она записывает все команды и может отвечать по-разному.
- `agents/claude-code/README.md` — описание `Artifacts`, и **исправлена запись о прогоне TASK-056**, где «`Artifacts` успешно читает историю коммитов» было записано как успех, хотя это и было проявлением дефекта.

### Изменённые файлы

- `agents/claude-code/container/script.go` — `BaseSHAFile`, запись базового SHA после клона.
- `agents/claude-code/executor.go` — `Artifacts` с диапазоном, `maxReportedCommits`, различение исходов.
- `agents/claude-code/executor_test.go` — фейк стал учитывать команду; обновлён существующий тест; 3 новых теста.

### Как проверялось

- **Дефект доказан фактом до исправления** (в отчёте TASK-085): на свежей ветке репозитория-песочницы `git log --format=%H%n%s -n 20` вернул `Initial commit` — коммит README, которого агент не делал.
- **Регрессионный тест подтверждён как ловящий дефект:** при возврате прежней команды падает с «git command = "git log --format=%H%n%s -n 20", want it limited to the range base000..HEAD».
- **Живая проверка до/после внутри образа исполнения** на настоящем репозитории:

  | Ситуация | Результат |
  | --- | --- |
  | До коммита агента, `<base>..HEAD` | **пусто** — унаследованный `Initial commit` исключён |
  | После одного коммита агента, `<base>..HEAD` | только `feat: agent-made commit` |
  | Прежняя команда без диапазона | **и коммит агента, и `Initial commit`** |

  Последняя строка — прямая демонстрация дефекта на том же репозитории и в том же контейнере.
- `make verify` — чисто; все тесты `agents/...` зелёные.

### Рекомендации

- **Фейк, игнорирующий аргументы, скрывает дефекты выбора.** Прежняя `fakeSandbox.Exec` возвращала один вывод на любую команду, поэтому тесты проверяли только разбор. Правило на будущее: если код решает, **какую** команду или запрос выполнить, фейк обязан различать команды — иначе тест не покрывает само решение. Тот же принцип применим к любому фейку, подменяющему внешний интерфейс.
- **Запись в документации о живом прогоне может закрепить дефект как успех.** В README TASK-056 наблюдение «Artifacts успешно читает историю» было зафиксировано как подтверждение работоспособности. Формулируя результат живой проверки, стоит спрашивать не «получилось ли», а «то ли это, что должно было получиться»: коммитов агента там быть не могло, значит непустой результат сам по себе был сигналом.
- Оба дефекта этого пакета (BUGFIX-006/007) существовали с EPIC-006 и нашлись одним сквозным прогоном. Это довод в пользу того, чтобы сквозная живая проверка с реальными внешними системами была отдельной задачей **каждого** эпика, который что-то интегрирует, а не только последнего.
