# TASK-104: Раздел v1.0.0 в CHANGELOG (без публикации тега)

## Тип

docs

## Эпик

[EPIC-014 Стабилизация и релиз](../../docs/roadmap/EPIC-014-stabilization-release.md)

## Цель

Подготовить репозиторий к публикации `v1.0.0`: перенести накопленное в `[Unreleased]` в датированный раздел версии по [релизному процессу](../../docs/development/git-workflow.md). **Тег не публикуется.**

## Контекст

Релизный процесс уже описан: семантическая версия, тег на `main`, раздел версии в CHANGELOG, GitHub Release с категоризацией по меткам. Здесь выполняется только та часть, которая обратима и принадлежит репозиторию.

**Почему тег не публикуется этой задачей.** Публикация тега и Release — необратимое внешнее действие: тег виден всем, кто следит за репозиторием, и снять его без следа нельзя. Решение «версия готова к публикации» принимает владелец проекта, а не исполнитель. Эпик доводит репозиторий до состояния «остаётся одна команда» и останавливается — тот же принцип, что контрольные точки самой платформы.

## Scope

### Входит

- Раздел `## [1.0.0] — 2026-XX-XX` в [CHANGELOG.md](../../CHANGELOG.md): содержимое `[Unreleased]` переносится, `[Unreleased]` остаётся пустым для последующей работы.
- Сводка версии: что платформа умеет к v1.0 (четыре роли, контрольные точки человека, Orchestrator/API/Dashboard, Memory) и **что осознанно не сделано** (аутентификация отложена, Tool Layer не реализован, содержательная работа агентов не проверена вживую) — без смягчения.
- Проверка соответствия релизному процессу: формат раздела, ссылки, порядок.

### Не входит

- **Публикация тега `v1.0.0` и GitHub Release** — решение владельца проекта.
- Изменение самого релизного процесса.
- Проставление версии в код: проект её нигде не хранит, и вводить хранилище версии ради релиза не требуется (проверить при выполнении; если где-то версия есть — обновить).

## Отчёт о выполнении

### Задача

TASK-104 — Раздел v1.0.0 в CHANGELOG (без публикации тега).

### Что сделано

**Раздел `[1.0.0] — 2026-07-27` сформирован** по релизному процессу ([git-workflow.md](../../docs/development/git-workflow.md)): содержимое `[Unreleased]` перенесено в него целиком, `[Unreleased]` оставлен пустым для последующей работы. До 1.0.0 версии не выпускались, поэтому вся история накопления оказалась в одном разделе — это отмечено в тексте, чтобы читатель не искал промежуточные версии.

**Сводка версии** написана двумя частями, обе обязательные по scope задачи:

- *Что платформа умеет* — четыре роли исполняют агенты; человек на двух контрольных точках, и платформа перед каждой останавливается; агент не имеет доступа к API, поэтому обойти точку не может структурно; перечислены составные части (API, Dashboard, Orchestrator, доменное ядро, PostgreSQL с журналом, GitHub, память с индексом в Qdrant).
- *Что осознанно не сделано* — семь пунктов без смягчения: нет аутентификации; Tool Layer не реализован; **содержательное качество работы агентов вживую не проверено** (названо единственным непроверенным участком версии, с оговоркой, что проверен зато отказ каждой из четырёх ролей); поиск в памяти не семантический; один исполнитель за раз и курсор в памяти; политика устаревания памяти не определена; документация только на русском. Каждый пункт со ссылкой на ADR или документ, где ограничение обосновано.

**Версия в коде.** Задача предполагала, что проект её нигде не хранит; проверка нашла одно место — `apps/dashboard/package.json` (`0.1.0`, пакет `private`, в npm не публикуется). Обновлено до `1.0.0`, чтобы единственное машиночитаемое упоминание версии не расходилось с релизом.

**`PROJECT_MANIFEST.md`** — поле Version переписано: v1.0.0 подготовлен, тег не опубликован, публикация — решение владельца.

### Что остаётся сделать владельцу проекта

Ровно две команды, обе — необратимые внешние действия и потому вне эпика:

```bash
git tag -a v1.0.0 -m "AI Studio OS v1.0.0"
git push origin v1.0.0
```

Затем — GitHub Release на этот тег (кнопка «Generate release notes» сгруппирует PR по меткам согласно [.github/release.yml](../../.github/release.yml); сгенерированное **не заменяет** раздел CHANGELOG, а дополняет его). До этого момента репозиторий находится в состоянии «остаётся одна команда»: раздел версии готов, версия в манифесте проставлена, ничего внешнего не опубликовано.
