# BUGFIX-009: платформа теряет ссылку на созданный Pull Request

## Тип

fix

## Эпик

Вне эпика — исправление; обнаружено при разборе TASK-094 (EPIC-012), затрагивает уже закрытые EPIC-004 (`CompletionService`, `TaskProjection`) и EPIC-010 (`apps/orchestrator`).

## Цель

`ReviewRequested` обязан нести ссылку на Pull Request — так записано в каталоге событий ([events.md](../../docs/architecture/events.md), «Данные: идентификатор задачи, **ссылка на PR**, автор изменений»). Реализация её не передаёт, поэтому ссылка на созданный платформой PR теряется безвозвратно, а команда приёмочного решения, которой она нужна для слияния, становится невыполнимой. Задача — довести ссылку от места создания PR до того, кто принимает решение.

## Контекст

Обнаружено при разборе TASK-094 (подтверждение решений из UI), **до написания кода UI**.

**Цепочка потери.** `apps/orchestrator/monitor.go`: `OpenPullRequest` возвращает `prID`, он используется для `RequestReview` у провайдера, логируется — и **отбрасывается**. Дальше его негде взять:

- `ArtifactStore` — только `Get`/`Save`, запросов нет;
- `GET /artifacts` не существует (артефакты вообще нельзя прочитать через API);
- `taskViewResponse` поля о PR не имеет;
- PR не записывается как Artifact, хотя утверждённая спецификация это прямо предусматривает ([artifact.md](../../docs/specifications/domain/artifact.md): «**Pull Request** — Type: PullRequest… Published — в момент слияния»).

**Почему это блокирует.** `CompletionService.CompleteTesting` при `Passed: true` требует `Repository` и `PullRequestID` — без них не выполнить `MergePullRequest` (порядок по [ADR-008](../../docs/adr/ADR-008-git-policies.md)). Значит **никто** — ни UI, ни другой клиент — не может принять положительное приёмочное решение: нужного идентификатора нет в системе.

**Почему не заметили раньше.** Тесты golden path передают `Repository`/`PullRequestID` явно — тест знает то, чего не знает реальный вызывающий код. Живые прогоны EPIC-010/011 до приёмочного решения не доходили: без `ANTHROPIC_API_KEY` агент не производит коммитов, PR не открывается. То есть дефект скрывался ровно в том промежутке, который не покрывался ни тестом, ни живой проверкой.

**Отрицательный исход не затронут:** `Passed: false` (вернуть на доработку) слияния не делает и ссылку не требует — этот путь работает.

## Scope

### Входит

- `internal/application/completion.go` — `RequestReview` принимает ссылку на Pull Request (репозиторий + идентификатор) и прикрепляет её к событию `ReviewRequested` через уже существующий механизм `Envelope.WithData` (тот же, что несёт `to` у `ReviewCompleted` и описательные поля у `TaskCreated`).
- `internal/application/projection.go` — `TaskView` получает ссылку на PR, заполняемую из данных `ReviewRequested`.
- `apps/api` — поле ссылки на PR в представлении задачи; `request-review` принимает её в теле; `complete-testing` перестаёт требовать `repository`/`pullRequestId`, когда платформа уже знает ссылку (совместимость: явно переданные значения имеют приоритет).
- `apps/orchestrator` — передаёт `prID`, который уже получил, вместо того чтобы его отбросить.
- `docs/api/tasks.md` — новое поле и изменение обеих операций.
- Тесты: ссылка доезжает от `RequestReview` до `TaskView`; выживает пересборку проекции из журнала (та же ловушка, что BUGFIX-004); приёмочное решение выполняется без явных `repository`/`pullRequestId`; отрицательный исход по-прежнему работает без ссылки.

### Не входит

- **Запись PR как Artifact** (`Type: PullRequest`, как предусматривает спецификация) — отдельный пробел против спецификации `artifact.md`, не нужный для разблокирования приёмочного решения. Фиксируется как Open Question, чтобы не потеряться: `Published` в момент слияния дал бы аудит слияний, но это самостоятельная задача, а не побочный эффект этой.
- Операции чтения артефактов через API (`GET /artifacts`) — тот же случай.
- Изменение доменных модулей: `internal/domain` не меняется, ссылка живёт в данных события и read-модели.

## Критерии приёмки

- [x] `ReviewRequested` несёт ссылку на Pull Request — как требует `events.md`.
- [x] Ссылка доступна в представлении задачи (`repository`/`pullRequestId`) и выживает пересборку проекции из журнала (механизм `WithData` читается структурно — BUGFIX-004).
- [x] Положительное приёмочное решение выполняется **без** передачи `repository`/`pullRequestId` вызывающим кодом — проверено юнит-тестом и через реальный HTTP.
- [x] Отрицательный исход (вернуть на доработку) работает как раньше, ссылки не требуя.
- [x] Orchestrator передаёт ссылку, а не отбрасывает.
- [x] `make verify` — чисто; весь набор `-tags integration` — зелёный.

## План реализации

1. `RequestReviewParams` вместо позиционных аргументов; ссылка прикрепляется к `ReviewRequested` через `WithData`.
2. `TaskView.Repository`/`PullRequestID`, заполняются из данных `ReviewRequested`; **только дополняют, никогда не стирают**.
3. `CompleteTesting` разрешает ссылку через `Views`, если не передана явно; неразрешимая — ошибка **до** публикации любого события.
4. Orchestrator возвращает `prID` из `openPullRequest` и передаёт в `RequestReview`; одна общая проекция на процесс.
5. API: `request-review` принимает ссылку, представление задачи её отдаёт, `complete-testing` больше её не требует.
6. Тесты, документация, `make verify`, полный набор `-tags integration`.

## Отчёт о выполнении

### Задача

BUGFIX-009 — платформа теряла ссылку на созданный Pull Request.

### Что сделано

- **`ReviewRequested` наконец несёт ссылку на PR** — то, что `events.md` требовал с самого каталога событий. Механизм не новый: `Envelope.WithData`, тот же, что несёт `to` у `ReviewCompleted` и описательные поля у `TaskCreated`.
- **`TaskView` получил `Repository`/`PullRequestID`**, заполняемые из данных события. **Только дополняют, никогда не стирают:** повторный запрос ревью без ссылки (человек вручную) не должен терять то, что платформа уже знала — закреплено отдельным тестом.
- **`CompleteTesting` сам находит ссылку** через проекцию, если вызывающий её не передал. Явно переданные значения имеют приоритет — это сохранило работоспособность существующих вызовов и позволяет слить PR, который платформа не открывала.
- **Разрешение ссылки — до публикации `TestsPassed`, а не в момент merge.** Иначе неразрешимая ссылка означала бы объявленный «успешный прогон тестов» для задачи, которая осталась в Testing: ADR-008 фиксирует порядок событий именно чтобы они описывали произошедшее. Закреплено тестом, проверяющим, что при неизвестной ссылке **не публикуется ни одного** события.
- **Orchestrator перестал отбрасывать `prID`** — `openPullRequest` его возвращает, `RequestReview` получает. Заодно процесс теперь использует **одну** проекцию на диспетчер и `CompletionService`: две отдельные оставили бы ссылку невидимой для того, кто её ищет.
- **API**: `request-review` принимает ссылку, представление задачи её отдаёт (человек, принимающий необратимое решение о слиянии, должен видеть, что именно сливает), `complete-testing` больше её не требует.
- **Ключи `WithData` перестали быть строковыми литералами.** Продюсер и консьюмер сидят по разные стороны границы, и опечатка в литерале провалилась бы точно так же тихо, как BUGFIX-004 — читатель просто ничего не находит. Все семь ключей объявлены один раз.

### Как проверялось

- **Регрессионные тесты подтверждены как ловящие дефект:** при удалении прикрепления ссылки падают три из четырёх новых тестов. Четвёртый (`UnknownPullRequestFailsBeforePublishing`) продолжает проходить — и это правильно: он проверяет поведение при **отсутствии** ссылки, то есть охраняет другое свойство. Проверять «падает ли тест без фикса» стоит по каждому тесту отдельно, а не по набору целиком.
- **Тест через реальный HTTP** обнаружил расхождение фикстуры с продакшеном: `testDeps()` собирал `CompletionService` **без** `Views`, хотя `apps/api/main.go` его передаёт. То есть фикстура была слабее продакшена, и без этого теста разница осталась бы незамеченной. Исправлено, с комментарием о причине.
- `make verify` — чисто (1486 ссылок). Весь набор `-tags integration` на живом PostgreSQL — зелёный.
- Полный прогон `go test ./...` — все пакеты зелёные.

### Open Questions

- **PR по-прежнему не записывается как Artifact**, хотя утверждённая спецификация (`docs/specifications/domain/artifact.md`) прямо описывает `Type: PullRequest` с `Published` в момент слияния. Для разблокирования приёмочного решения это не требовалось, поэтому сознательно не делалось здесь. Отдельный пробел против спецификации: он дал бы аудит слияний и полноту модели артефактов.
- **Артефакты нельзя прочитать через API** (`GET /artifacts` не существует) — обнаружено попутно, к этой задаче не относится.

### Рекомендации

- **«Данные события» в каталоге — это требование, а не описание.** `events.md` перечислял ссылку на PR среди данных `ReviewRequested`, и расхождение с реализацией жило до первой попытки этими данными воспользоваться. Стоит сверять фактические полезные нагрузки событий с каталогом — это второй случай подряд (после долга ADR-007 в `workflow.md`), когда документ фиксировал требование, которого в коде нет.
- **Дефект нашёлся разбором перед кодом, а не после.** Если бы TASK-094 начиналась с UI, обнаружилось бы это на этапе «почему кнопка не работает» — и, вероятнее всего, лечилось бы просьбой к человеку ввести номер PR вручную. Полезно перед реализацией проверять, откуда возьмётся каждое обязательное поле запроса.
- **Тестовая фикстура, собранная слабее продакшена, скрывает дефекты интеграции.** `testDeps()` без `Views` — та же болезнь, что фейк, игнорирующий команду (BUGFIX-007): фикстура должна повторять сборку продакшена, иначе тест проверяет не ту систему.
