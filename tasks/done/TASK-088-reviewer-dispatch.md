# TASK-088: Бутстрап и диспетчеризация Reviewer

## Тип

feature

## Эпик

[EPIC-011 Роли исполнителей](../../docs/roadmap/EPIC-011-executor-roles.md)

## Цель

Автоматизировать роль Reviewer: на событие `ReviewRequested` Orchestrator запускает агента роли Reviewer, читает его вердикт и применяет через `CompletionService.CompleteReview` — задача уходит в Testing при одобрении или обратно In Progress при запросе правок.

## Контекст

Автоматизация Reviewer разрешена [ADR-008](../../docs/adr/ADR-008-git-policies.md) (агент-ревьюер допустим) и не обходит контрольные точки [ADR-007](../../docs/adr/ADR-007-pm-qa-executors.md), которые названы только для DoR и финального Done. Вердикт ревью не сливает код: слияние произойдёт на шаге QA, остающемся за человеком до третьего эпика декомпозиции.

Механизм диспетчеризации и слежения уже построен (EPIC-010) — эта задача добавляет вторую роль в существующий цикл, а не строит новый. Предпосылка — TASK-086: с двумя записями в реестре расхождение «выбрана одна, работает другая» стало бы наблюдаемым.

**Что ревьюит агент.** Ветка задачи выводится той же детерминированной функцией, что и при создании (`branchName`), поэтому дополнительных данных не требуется. Ограничение: если Pull Request открыт человеком на ветке с другим именем, Reviewer не найдёт изменения — для v1.0, где ветку создаёт сам Orchestrator, это верно.

## Scope

### Входит

- Бутстрап Reviewer-исполнителя — идемпотентно, по образцу Developer (фиксированный идентификатор как механизм идемпотентности).
- Обработка `ReviewRequested` в `Dispatcher`: сборка `platform.ExecutorTask` с ролью Reviewer и координатами ветки, запуск агента, слежение до терминального состояния (переиспользуя механизм TASK-083).
- Чтение вердикта после успешного исполнения и применение через `CompletionService.CompleteReview(approved)`.
- **Отсутствие вердикта по умолчанию.** Неудача агента, таймаут или нераспознанный вердикт оставляют задачу в Review — решение переходит к человеку. Ни «одобрено», ни «нужны правки» не выдумывается: выдуманное одобрение продвинуло бы код к слиянию без реальной проверки.
- `Executor.Finish` — всегда, как и для Developer.
- Тесты: одобрение → Testing; запрос правок → In Progress; неудача агента → задача осталась в Review, `CompleteReview` не вызван; нераспознанный вердикт → то же; `Finish` вызван во всех путях; событие не `ReviewRequested` → диспетчеризации нет.

### Не входит

- Диспетчеризация PM и QA — перенесена в эпик после механизма подтверждения человеком.
- Эскалация ревью к человеку (ADR-008 допускает) — требует механизма подтверждения.
- Оценка содержательного качества вердикта — за человеком.

## План реализации

### Решения, принятые при разборе

**1. Ревью не создаёт Execution — и это надо зафиксировать честно.** `WorkService.StartTask` — единственный путь создать Execution, но он делает переход Ready → In Progress, которого при ревью не происходит (задача уже в Review). Отдельного use-case «создать Execution без перехода» в Application Layer нет, и добавлять его — расширение закрытого слоя за пределами этой задачи.

Следствие: работа ревьюера не отражается событиями `ExecutionQueued`/`Started`/`Succeeded`, то есть в журнале и Dashboard её не видно так, как видно работу разработчика. Единственный след — пара `ReviewRequested` → `ReviewCompleted`. Это приемлемо (`ReviewCompleted` и есть запись о ревью), но должно быть записано как ограничение, а не остаться незамеченным.

**2. `Verdict` нельзя читать прямо из `Dispatcher`.** Метод есть у конкретного `claudecode.Executor`, а `Dispatcher` по границам знает только `platform.Executor` (`module-boundaries.md`; узкое исключение выдано **только** `main.go` как composition root, и README это утверждает). Импортировать `claudecode` в `dispatch.go` — нарушить границу и сделать документацию неверной.

Решение: интерфейс в `apps/orchestrator` с примитивными возвращаемыми значениями (без общего типа), а адаптацию конкретного `claudecode.Executor` к нему делает `main.go` — ровно там, где исключение уже разрешено:

```go
type ReviewExecutor interface {
    platform.Executor
    Review(ctx context.Context) (approved bool, comment string, err error)
}
```

**3. Ветка не создаётся** — она уже существует (её создал Orchestrator при диспетчеризации Developer). Имя выводится той же функцией `branchName`. Если Pull Request открыт человеком на ветке с другим именем, клон не найдёт её и `Accept` упадёт — задача останется в Review общим отказным путём; ограничение документируется.

### Шаги

1. `monitor.go` — `waitForTerminalStatus` принимает `label string` вместо `executionContext` (использовался только для сообщений), чтобы годиться и для ревью, у которого Execution нет.
2. `dispatch.go`:
   - поле `NewReviewer func() (ReviewExecutor, error)` — отдельно от `NewExecutor`, потому что ревью требует возможности сверх контракта;
   - `Handle` реагирует и на `ReviewRequested`;
   - `dispatchReviewRequested` — представление задачи, свой Reviewer-исполнитель (`executorForRole`), репозиторий, имя ветки, `ExecutorTask{Role: reviewer}`, `Accept`, затем слежение и применение вердикта.
3. Применение вердикта: `defer Finish` (всегда); ожидание терминального состояния; при успехе — `Review(ctx)` и `CompletionService.CompleteReview(approved)`.
4. **Вердикта по умолчанию нет.** Отказ агента, таймаут, отсутствующий или нераспознанный вердикт — задача остаётся в Review, `CompleteReview` не вызывается. Выдуманное одобрение продвинуло бы код к слиянию без реальной проверки; выдуманный отказ отправил бы разработчика переделывать без причины.
5. `main.go` — бутстрап Reviewer (`EnsureExecutor(..., shared.RoleReviewer)`), фабрика `NewReviewer` с тонкой обёрткой над `claudecode.Executor`.
6. Тесты: одобрение → Testing; запрос правок → In Progress; отказ агента → осталась в Review и `CompleteReview` не вызван; нераспознанный вердикт → то же; таймаут → то же; `Finish` во всех путях; событие не `ReviewRequested`/`TaskPlanned` → диспетчеризации нет; у ревьюера в `ExecutorTask` роль `reviewer` и та же ветка.
7. `make verify`.

### Open Questions

- **Работа ревьюера не видна в журнале так, как работа разработчика** — нет `ExecutionQueued`/`Started`/`Succeeded`, только пара `ReviewRequested` → `ReviewCompleted`. Причина: единственный путь создать Execution (`WorkService.StartTask`) делает переход Ready → In Progress, которого при ревью не происходит. Если наблюдаемость ревью понадобится (например, для Dashboard), понадобится use-case «создать Execution без перехода» — расширение Application Layer, отдельное решение.
- Содержательное качество вердикта платформа проверить не может; эскалация к человеку (ADR-008 её допускает) требует механизма подтверждения — третий эпик.

### Рекомендации

- **Обобщение ради второго случая оправдалось буквально.** `EnsureExecutor` и вывод идентификатора из роли делались в TASK-086 как исправление дефекта; вторая роль после этого добавилась вызовом, а не копией функции. Стоит и дальше обобщать в тот момент, когда второй случай уже виден, — не раньше и не позже.
- **Документированное ограничение стоит закреплять тестом.** Фраза «ревью не создаёт Execution» без теста разошлась бы с кодом при первой же правке. Это дешёвая страховка против того самого класса расхождений, который в этом проекте уже дважды всплывал.
- Когда появится ключ провайдера, для ревью важно проверить не «согласен ли я с вердиктом», а **соблюдает ли агент конвенцию** и корректно ли платформа ведёт себя, когда он её не соблюдает: второй случай сейчас покрыт только фейками.
