# TASK-094: Dashboard — подтверждение решений (первый мутирующий UI)

## Тип

feature

## Эпик

[EPIC-012 Контрольные точки человека](../../docs/roadmap/EPIC-012-human-checkpoints.md)

## Цель

Дать человеку принять решение из интерфейса: приём Definition of Ready и финальное приёмочное решение. Это **первый мутирующий UI** в проекте.

## Контекст

`apps/dashboard` полностью read-only: ни одной формы, ни одного мутирующего запроса, ни одного обработчика ошибки записи ([EPIC-009](../../docs/roadmap/EPIC-009-dashboard.md) отложил их «до реальной потребности»). Потребность наступила: подтверждение — это действие, и без него контрольная точка остаётся невидимой в UI.

Команды уже существуют и не меняются: `POST .../plan` (приём DoR) и `POST .../complete-testing` (приёмочное решение). Новая здесь — **категория кода**, а не эндпоинт: запись из UI, обработка отказа, обновление данных после успеха.

Приёмочное решение сливает Pull Request ([ADR-008](../../docs/adr/ADR-008-git-policies.md)), то есть это действие с внешним эффектом и необратимое в рамках задачи. Интерфейс обязан показывать это до нажатия, а не после.

## Scope

### Входит

- Действие «принять Definition of Ready» для задачи в Backlog.
- Действие «принять» / «вернуть на доработку» для задачи в Testing (второе выражается уже существующим `complete-testing` с отрицательным исходом — новых команд не вводится).
- **Обработка отказа:** ошибка запроса показывается пользователю; интерфейс не показывает устаревшее состояние как актуальное; повтор возможен.
- **Обновление данных после успеха** — список ожидающих и состояние задачи отражают результат.
- Предупреждение о внешнем эффекте приёмочного решения (слияние Pull Request) до подтверждения.
- Тесты: успешное действие, отказ сервера, отображение результата.

### Не входит

- Новые эндпоинты и изменение существующих.
- Аутентификация: платформа не отличает человека от агента (ADR-012) — ограничение фиксируется документацией (TASK-091), а не решается здесь.
- Массовые действия и произвольное редактирование задач.

## Критерии приёмки

## План реализации

### Решения, принятые при разборе

**1. Запись — через Server Actions, а не `fetch` из браузера.** `apps/api` **не отдаёт CORS-заголовков** (проверено), поэтому запрос из браузера на другой порт был бы заблокирован. Server Actions выполняются на сервере Next.js, который и так общается с API, — CORS не возникает вовсе, адрес API остаётся серверным, а обновление данных делается `revalidatePath`. Альтернатива потребовала бы добавить CORS в API ради UI, то есть расширить публичную поверхность из-за детали клиента.

**2. Ошибка действия возвращается значением, а не исключением.** `error.tsx` — Error Boundary для отказов **рендера**: он заменяет страницу целиком. Для неудавшегося действия это неверно — человек теряет контекст и не видит, что именно не получилось. Действия возвращают результат (`ok` либо текст ошибки), UI показывает его рядом с кнопкой и позволяет повторить.

**3. Отрицательный исход выражается существующей командой.** «Вернуть на доработку» — это `complete-testing` с `passed=false`; новых эндпоинтов не вводится (`workflow.md`: отрицательные исходы уже покрыты переходами).

**4. Приёмочное решение показывает последствие до нажатия.** Требование записано нормативно в `workflow.md` (TASK-091): решение сливает Pull Request (ADR-008) и необратимо в рамках задачи. После BUGFIX-009 ссылка на PR доступна в представлении задачи, поэтому показывается **какой именно** PR будет слит, а не только предупреждение.

### Шаги

1. `src/lib/api.ts` — хелпер `post`; типы результата действия.
2. `src/lib/actions.ts` (`"use server"`) — `acceptDefinitionOfReady`, `acceptTask`, `returnForRework`; каждое при успехе делает `revalidatePath` для списка решений и страницы задачи.
3. `src/app/decisions/DecisionActions.tsx` (`"use client"`) — кнопки, состояние «выполняется» через `useTransition`, показ ошибки рядом с кнопкой, предупреждение о слиянии с указанием PR.
4. Встроить в `/decisions`; на странице задачи — те же действия, если это не требует переделки страницы.
5. Тесты: успешное действие вызывает нужное действие и показывает результат; отказ показывает сообщение и не выдаёт устаревшее состояние за актуальное; предупреждение о слиянии присутствует до нажатия.
6. `README`; проверки `apps/dashboard` и `make verify`.

## Отчёт о выполнении

### Задача

TASK-094 — подтверждение решений из интерфейса; первый мутирующий UI в проекте.

### Что сделано

- **Server Actions вместо `fetch` из браузера.** `apps/api` не отдаёт CORS-заголовков — запрос из браузера на другой порт был бы заблокирован. Server Action выполняется на сервере Next.js, который и так общается с API: CORS не возникает, адрес API остаётся серверным. Альтернатива означала бы добавить CORS в API ради детали клиента.
- **Три действия**: приём Definition of Ready (`plan`), приёмочное решение (`complete-testing` с `passed=true`), возврат на доработку (`passed=false`). Новых эндпоинтов не вводилось — отрицательные исходы уже покрыты переходами state machine.
- **Ошибка действия — значение, а не исключение.** `error.tsx` заменяет страницу целиком, что верно для отказа рендера и неверно для отказа действия: человек теряет контекст и не видит, что не получилось. Ошибка показывается рядом с кнопкой (`role="alert"`), повтор возможен сразу.
- **Текст ошибки API доводится до человека**, а не подменяется кодом статуса: «переход недопустим» и «задача не найдена» требуют разных действий от того, кто это увидит. Сетевой отказ (`fetch failed`) тоже показывается, а не замалчивается.
- **`revalidatePath` только при успехе.** После отказа состояние не изменилось, и обновлять данные значило бы выдать прежнее за новое.
- **Приёмочное решение предупреждает до нажатия и называет Pull Request.** Требование записано нормативно в `workflow.md` (TASK-091); ссылка доступна благодаря BUGFIX-009, поэтому человек видит **что именно** сольёт, а не абстрактное предупреждение.
- **Кнопка приёма DoR названа коротко** («Принять»): рядом уже стоит название решения из `decisionLabels`, и дублирование текста было и шумом, и коллизией в тесте — исправлено в UI, а не смягчением проверки.

### Open Questions

- **Вживую действия ещё не проверены** — это TASK-095. Тесты работают на моках Server Actions, то есть проверяют компонент, а не связку «браузер → Next.js → API → БД». Уроки EPIC-010/011 говорят, что дефекты живут именно в таких швах.

### Рекомендации

- **Отсутствие CORS у API — архитектурно значимая деталь для UI.** Она делает Server Actions единственным разумным путём записи из этого интерфейса. Стоит помнить при добавлении любых новых мутаций: попытка сделать их клиентским `fetch` упрётся в то же ограничение, и правильный ответ — не добавлять CORS, а идти через сервер.
- **`error.tsx` не подходит для отказов действий.** Error Boundary заменяет страницу; для кнопки нужен локальный показ. Разделение стоит держать явным: рендер — граница, действие — значение.
- **Совпадение текста кнопки с соседней подписью — сигнал, а не помеха тесту.** Тест упал на неоднозначности, и правильным ответом было убрать дублирование в UI, а не ослабить поиск до `getAllByText`.
