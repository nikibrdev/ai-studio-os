# TASK-107: Сценарий прогона и критерии оценки содержательной работы

## Тип

docs

## Эпик

[EPIC-015 Проверенная работа агентов](../../docs/roadmap/EPIC-015-verified-agent-work.md)

## Цель

Записать **до** первого живого прогона, что именно будет прогоняться и по каким признакам результат будет признан содержательной работой, а не формальным завершением.

## Контекст

Первый прогон с настоящим ключом даёт единственную возможность увидеть непредвзятую картину: как только результат известен, критерии неизбежно подстраиваются под него — не по злому умыслу, а потому что наблюдение выглядит осмысленным задним числом. Поэтому они пишутся раньше.

Опыт эпиков даёт уже проверенный приём: **отрицательные проверки**. Утверждение «агент выполнил задачу» доказывается не тем, что задача в нужном состоянии (она могла попасть туда и без работы агента), а тем, что появились следы работы, которых иначе не бывает. Так же EPIC-013 доказывал остановку на контрольных точках — счётчиком не случившихся событий.

Риск, который эти критерии обязаны исключить: агент, завершившийся с кодом 0, без коммитов или с коммитом-заглушкой, выглядит в журналах платформы неотличимо от успеха.

## Scope

### Входит

- **Сценарий**: конкретная задача для роли Developer в репозитории-песочнице — минимальная из доказывающих, что агент действительно программирует (изменение с проверяемым результатом, а не «создай файл»). Прогоны тратят средства владельца, поэтому дешевизна сценария — требование, а не удобство.
- **Критерии оценки по каждой из четырёх ролей**: что считается содержательным результатом, что — формальным завершением, что — провалом.
- **Отрицательные проверки** для каждой роли: какие следы обязаны появиться и каких быть не должно.
- **Что фиксировать во время прогона**: журналы платформы и агента, состояние задачи, произведённые артефакты, время и (если доступно) расход токенов.
- Документ в `engineering/` — свидетельство, а не документация системы.

### Не входит

- Сам прогон — TASK-108/109.
- Правка промптов ролей: сначала измеряется то, что есть.
- Автоматизация оценки: критерии применяет человек, читая результат.

## Критерии приёмки

- [ ] Сценарий задачи для Developer описан настолько конкретно, что прогон воспроизводим другим человеком.
- [ ] По каждой из четырёх ролей определено, что считается содержательным результатом, формальным завершением и провалом.
- [ ] По каждой роли названа хотя бы одна отрицательная проверка.
- [ ] Названо, что именно фиксируется во время прогона.
- [ ] Документ утверждён **до** начала TASK-108 — то есть слит раньше.
- [ ] `make verify` — чисто.
