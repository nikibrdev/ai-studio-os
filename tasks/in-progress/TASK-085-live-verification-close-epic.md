## Scope

### Входит

- Запуск `docker compose up` (PostgreSQL), применение миграций, запуск `apps/orchestrator` (`go run`).
- Через `apps/api` (или напрямую через Application Layer в тестовом сценарии) — создание проекта, подключение репозитория, активация, создание и планирование задачи (`TaskPlanned`).
- Наблюдение: Orchestrator подхватывает событие, создаёт ветку, запускает контейнер, задача переходит в In Progress; по завершении контейнера — либо переход в Review с открытым PR (если AI-провайдер доступен и отработал), либо честно задокументированная остановка на этапе механики (если ключа нет).
- Обновление раздела «Критерии завершения» EPIC-010 (отметки `[x]`), `ROADMAP.md` (прогресс v1.0), `PROJECT_MANIFEST.md`, `PROJECT_HEALTH.md`, `CHANGELOG.md`.

### Не входит

- Открытие следующего эпика декомпозиции v1.0 («Роли PM/QA») — отдельная задача после этой.

## План реализации

**Решение владельца проекта (2026-07-25):** сквозная проверка выполняется против **одноразового репозитория**, а не против `ai-studio-os` — чтобы автоматически созданные ветка и Pull Request не оставляли следа в основном репозитории. Создан `nikibrdev/ai-studio-os-e2e-sandbox` (private, с начальным коммитом на `main`); удаляется одной командой после проверки.

**Что доступно и чего нет:**

| Условие | Состояние |
| --- | --- |
| PostgreSQL | есть (`docker compose`) |
| Образ `ai-studio-os-execution` | есть (собран в EPIC-006/TASK-053) |
| Действительный `GITHUB_TOKEN` | есть (через уже выполненную аутентификацию `gh`, scope `repo`) |
| `ANTHROPIC_API_KEY` | **нет** — агент запустится, но реального вызова провайдера не будет |

Отсутствие ключа провайдера — то же принятое ограничение, что зафиксировано в EPIC-006 (Open Question TASK-056). Оно означает, что агент не напишет код, поэтому **содержательная** часть (реальные коммиты → Pull Request с кодом) непроверяема. Проверяемо всё остальное, включая то, что раньше было недостижимо: реальное создание ветки в GitHub, реальный запуск и уничтожение контейнера, реальное поведение `Artifacts`/`Status`.

### Шаги

1. Поднять `apps/api`, создать проект, подключить репозиторий-песочницу, активировать, создать и запланировать задачу — всё через реальные HTTP-вызовы, без прямых обращений к БД.
2. Запустить `apps/orchestrator` с действительным токеном и собранным образом.
3. Наблюдать и зафиксировать: подхват `TaskPlanned` из журнала → выбор исполнителя → **реальное создание ветки** → `StartTask` → **реальный запуск контейнера** → `Status` → `Artifacts` → исход → `Finish`.
4. Проверить в GitHub: ветка создана; Pull Request — открыт или нет, и почему.
5. Проверить в БД: состояния задачи и Execution, последовательность событий в журнале.
6. **Отдельно проверить подозрение, найденное при подготовке:** `Artifacts` выполняет `git log --format=%H%n%s -n 20` без ограничения диапазона, то есть возвращает историю ветки целиком, а не только коммиты, сделанные исполнением. На репозитории с существующей историей это означало бы, что чужие коммиты записываются как «произведённые» артефакты. Подтвердить или опровергнуть **фактом**, а не чтением кода.
7. По результатам: закрыть критерии эпика честно (что подтверждено, что осталось ограничением), обновить ROADMAP/PROJECT_MANIFEST/PROJECT_HEALTH/CHANGELOG, при необходимости открыть BUGFIX на найденное.
8. Удалить репозиторий-песочницу.
