# BUGFIX-011: Claude Code CLI отказывается стартовать под root — ни одна роль не запускается

## Тип

fix

## Эпик

Вне эпика — исправление; обнаружено при подготовке к живому прогону [EPIC-015](../../docs/roadmap/EPIC-015-verified-agent-work.md) (TASK-108), затрагивает закрытый EPIC-006 (`agents/claude-code`).

## Цель

Команда, которую платформа запускает внутри песочницы, не выполняется вообще: Claude Code CLI отказывается работать в режиме обхода разрешений от имени root. Это блокирует **все четыре роли**, а не только Developer. Задача — сделать так, чтобы CLI действительно запускался внутри образа исполнения.

## Контекст

`claudeCommand` строит вызов ([prompt.go:49](../../agents/claude-code/prompt.go)):

```go
[]string{"claude", "--print", "--permission-mode", "bypassPermissions", prompt}
```

Образ исполнения не переключает пользователя ([docker/execution/Dockerfile](../../docker/execution/Dockerfile) заканчивается на `WORKDIR /workspace`), поэтому команда идёт от root.

**Подтверждено фактом** внутри собранного образа `ai-studio-os-execution` (CLI версии 2.1.216):

```text
$ claude --print --permission-mode bypassPermissions "say hi"
--dangerously-skip-permissions cannot be used with root/sudo privileges for security reasons
```

Ответ провайдера не запрашивается — CLI останавливается до всякой сети. То есть при прогоне TASK-108 исполнение завершилось бы, не сделав ничего, и по критериям TASK-107 это исход **«провал»** (агент не обратился к провайдеру), известный заранее.

**Почему не поймали раньше.** Комментарий в `prompt.go` прямо говорит: «Exact CLI flag behavior is confirmed against the real Claude Code CLI in TASK-056» — но TASK-056 не дошёл до вызова CLI из-за отсутствия ключа, и предположение о поведении флага осталось непроверенным. Юнит-тесты адаптера проверяют, что команда **построена** правильно, а не что она **выполняется**: песочница в них фейковая.

**Проверены два обхода**, оба снимают отказ (дальше CLI доходит до `Not logged in · Please run /login`, то есть до ожидаемого отсутствия ключа):

| Вариант | Результат |
| --- | --- |
| `-e IS_SANDBOX=1` при том же root | `Not logged in` — root-проверка пройдена |
| `--user 1000:1000` с `HOME=/tmp` | `Not logged in` — root-проверка пройдена |

## План реализации

**Решение принято владельцем 2026-08-11: Вариант A.** Оба варианта записаны здесь как они были предъявлены к решению — B не выбран, но остаётся известным запасным путём.

**Вариант A — непривилегированный пользователь в образе.** В `Dockerfile` создать пользователя, задать ему `HOME`, передать владение рабочим каталогом; `docker run` и `docker exec` идут от него. Устраняет причину, а не признак: CLI отказывает именно потому, что обход разрешений от root опасен, и в этом он прав. Дороже: нужно согласовать владение клоном, `/tmp`-файлами (`BaseSHAFile`, `VerdictFile`, `ProposalFile`, `ReportFile`) и кэшем Go/npm.

**Вариант B — `IS_SANDBOX=1`.** Одна строка в `docker run` ([lifecycle.go](../../agents/claude-code/container/lifecycle.go), рядом с `HTTP_PROXY`; не секрет, argv допустим). Дёшево, но опирается на внутреннюю переменную CLI, не описанную в его публичном контракте: она может измениться в любой версии, и тогда платформа снова встанет — молча, тем же способом.

**Рекомендация: A.** Образ уже называется песочницей, и запуск агента от root в ней — не то, что кто-либо выбирал сознательно; это осталось по умолчанию от базового образа. B чинит симптом ценой скрытой зависимости от недокументированного поведения.

Шаги (для A):

1. `docker/execution/Dockerfile` — создать пользователя, `HOME`, владение `/workspace`; `USER` в конце.
2. `container/lifecycle.go` — убедиться, что `docker exec` идёт от того же пользователя (иначе `Exec` создаст файлы, недоступные агенту).
3. `container/script.go` — проверить пути `/tmp`-файлов на доступность записи.
4. Тесты: `lifecycle_test.go` / `script_test.go` фиксируют пользователя; интеграционный тест на реальном Docker.
5. Живая проверка внутри образа; `make verify`.

## Отчёт о выполнении

### Задача

BUGFIX-011 — Claude Code CLI отказывался стартовать под root, из-за чего не выполнялась команда ни одной из четырёх ролей.

### Что сделано

- **Образ исполнения работает от пользователя `agent`, а не от root.** `useradd`, владение `/workspace`, `USER`, явный `HOME`. Выбран Вариант A: причина устраняется, а не обходится — обход разрешений от root действительно опасен, и CLI в этом прав. Запуск от root не был чьим-то решением, он достался по умолчанию от базового образа.
- **`GOBIN=/usr/local/bin` для `gofumpt` и `golangci-lint`.** Побочное следствие смены пользователя, найденное до прогона, а не им: по умолчанию `go install` кладёт бинарники в `/root/go/bin`, недоступный `agent` ни по PATH, ни по правам. Роли Reviewer и QA прогоняют проверки проекта именно этими инструментами, так что без этого шага смена пользователя сломала бы их вместо того, чтобы починить.
- **Интеграционный тест `TestManager_Start_RunsUnprivileged`** на настоящем Docker: проверяет, что контейнер не работает от root и что CLI **проходит** свою root-проверку. Свойство закреплено за наблюдаемым поведением контейнера, а не за строкой в `Dockerfile`: юнит-тест здесь бессилен — пользователь есть свойство образа, а отказ приходит из CLI внутри него.
- **Снято непроверенное утверждение в `prompt.go`.** Комментарий гласил, что поведение флагов «confirmed against the real Claude Code CLI in TASK-056». TASK-056 до CLI не дошёл — ключа не было. Утверждение было унаследованным, а не проверенным, и ровно оно скрывало отказ.

### Как проверялось

- **Дефект доказан фактом до исправления**, внутри собранного образа (CLI 2.1.216):

  ```text
  $ claude --print --permission-mode bypassPermissions "say hi"
  --dangerously-skip-permissions cannot be used with root/sudo privileges for security reasons
  ```

- **После исправления, в том же образе:**

  | Проверка | Результат |
  | --- | --- |
  | `whoami` | `agent` |
  | `which gofumpt` / `golangci-lint` | `/usr/local/bin/...` |
  | Запись в `/workspace` и `/tmp` | OK |
  | `go build` (кэш в `HOME`) | OK |
  | `claude --print --permission-mode bypassPermissions` | `Not logged in · Please run /login` |

  Последняя строка и есть искомое: дойти до аутентификации — значит пройти root-проверку. Дальше нужен ключ, которого нет.

- **Интеграционный тест на настоящем Docker** — `TEST_DOCKER=1 go test -tags=integration -run TestManager_Start_RunsUnprivileged`: PASS за 12.9 с, полным циклом через клон и прокси; вывод контейнера — `agent` / `Not logged in` / `done`.

### Рекомендации

- **Комментарий, ссылающийся на проверку, которой не было, опаснее отсутствия комментария.** «Confirmed against the real CLI in TASK-056» читалось как основание не проверять — при том что TASK-056 явно закрылся с Open Question о недоступности ключа. Правило: утверждение о внешнем поведении либо привязано к тесту, который его проверяет, либо помечено как непроверенное.
- **Смена пользователя ломает всё, что установлено в `HOME` сборщика.** `GOBIN` понадобился не потому, что о нём подумали заранее, а потому что проверка запускалась вживую. Любой будущий инструмент в этом образе нужно ставить общесистемно.
- Дефект существовал с EPIC-006 и был бы найден первым же прогоном с ключом — то есть за деньги владельца. Дешёвая проверка «запускается ли команда вообще» внутри образа стоит того, чтобы входить в эпик, который эту команду вводит.
